# AVProject 面试问答复盘

## 使用方法

不要逐字背诵。建议每题按四层组织：

```text
先说结论
  -> 再说当前实现
  -> 再说设计取舍
  -> 最后说不足和优化
```

面试时必须区分“已经完成”和“计划优化”。例如当前主线 `AVServer` 是阻塞式单连接服务器，不能描述成已经使用 epoll 和线程池；epoll/线程池存在于原始参考工程，是下一步整合方向。

# 一、项目整体类

## Q1：这个项目是做什么的？

**回答：**

这是一个 Windows 客户端加 Ubuntu 服务端的 C/S 音视频系统。Windows 端基于 Qt、FFmpeg、SDL、OpenGL 和 OpenCV，提供本地播放、桌面录制、远程媒体列表、分片上传和分片下载；Ubuntu 端通过 TCP 自定义协议管理 `media/` 目录，处理列表、上传和下载。

当前完整闭环是：本地录制或选择媒体，上传到服务端，刷新远程媒体列表，再下载到客户端 cache，最后复用本地播放器播放。项目重点不是做商业视频平台，而是把音视频、网络、线程、文件传输和工程化组织串成一个可运行系统。

## Q2：为什么把播放器、录制器和 C/S 结合，而不是保留三个独立 Demo？

**回答：**

独立 Demo 只能证明单点 API 会用，整合项目还要解决模块边界、对象生命周期、线程通信、协议设计、跨平台构建和错误闭环。播放器输出消费能力，录制器产生媒体，C/S 模块让媒体可以远程管理，三者组合后才有真实业务流。

整合时我没有重写成熟的音视频核心，而是增加 Page 适配层、共享网络服务和协议管理器。这能说明我不仅能实现算法或 API，还能控制改动范围、复用已有模块并处理跨模块协作。

## Q3：项目的完整业务闭环是什么？

**回答：**

客户端可以录制桌面、摄像头和麦克风，生成本地 FLV；也可以选择其他本地媒体。Remote Media 页面将文件按 64 KB 分片上传，服务端先写 `temp/`，完整后移动到 `media/`。客户端刷新列表后选择远程文件，按 offset 分片下载到 `cache/*.part`，完成后改成正式文件，并调用本地播放器播放。

这个闭环覆盖“媒体产生、传输、服务端管理、获取和消费”。Ping 和媒体列表是控制面，上传下载是数据面，播放器和录制器是本地音视频能力。

## Q4：你在项目中具体完成了哪些工作？

**回答：**

可以按阶段回答：我先审查四个原始工程，保留播放器和录制器核心；然后创建统一 Qt Widgets 客户端，把播放、录制、远程媒体和设置页面整合进主窗口。之后实现 Windows Winsock 客户端、Ubuntu TCP 服务端和长度帧协议，再增加媒体列表、分片上传、分片下载以及下载后自动播放。

工程层面还包括相对依赖路径、DLL 部署脚本、运行目录隔离、`.gitignore`、阶段日志、架构和协议文档。回答时应明确哪些核心来自原始学习项目，哪些整合与网络功能是后续实现，避免把所有代码都说成从零编写。

## Q5：这个项目最关键的设计取舍是什么？

**回答：**

第一，优先打通最小闭环，不一开始整合 epoll、MySQL 和边下边播。第二，播放器与录制器采用薄适配复用，不重构音视频核心。第三，文件传输使用 64 KB 串行分片，牺牲极限吞吐换取简单状态和稳定 offset。第四，上传使用 temp，下载使用 `.part`，避免半成品进入正式目录。

这些取舍的共同原则是把风险拆开：先确认每个阶段可编译、可运行、可回归，再讨论并发和性能。

## Q6：当前项目最值得讲的工程能力是什么？

**回答：**

一是跨模块边界：UI、音视频工作线程、TCP 收包线程和文件系统各自负责明确职责。二是协议状态机：INIT、BLOCK、FINISH 让大文件传输有建立、推进和提交边界。三是失败语义：上传半成品留在 temp，下载半成品使用 `.part`，断线后不把它们当正式媒体。

另外，文档明确记录当前服务端仍是单连接阻塞模型，这种对现状和限制的准确判断也属于工程能力。

# 二、播放模块类

## Q7：MediaPlayer 的整体播放流程是什么？

**回答：**

`PlayerDialog` 获取文件路径后调用 `VideoPlayer::setFileName()` 和 `start()`。`VideoPlayer` 继承 `QThread`，在线程中用 FFmpeg 打开输入、查找流、循环 `av_read_frame()`，把音频和视频 packet 分别放进两个 `PacketQueue`。

SDL 音频回调从音频队列取 packet、解码和重采样后送声卡；视频线程从视频队列取 packet、解码和转换图像，再通过 Qt signal 交给 OpenGL 控件显示。UI 线程只处理按钮、进度和图像展示，不执行持续解封装。

## Q8：FFmpeg 在播放模块里负责什么？

**回答：**

FFmpeg 负责输入协议和容器解析、流信息发现、音视频解码、时间戳以及格式转换。具体包括 `avformat_open_input`、`avformat_find_stream_info`、`av_read_frame`、解码器上下文、`swresample` 音频重采样和 `swscale` 图像格式转换。

FFmpeg 不直接负责 Qt 页面，也不直接负责声卡和最终 OpenGL 控件。项目把“媒体处理”与“设备输出/UI”分开。

## Q9：SDL 在项目中负责什么？

**回答：**

播放端 SDL 主要负责音频设备回调、线程/定时机制以及 packet 队列需要的 mutex 和 condition variable。音频设备主动拉取数据时触发回调，因此音频播放节奏由实际设备消费驱动。

SDL 不是解码器。压缩数据仍由 FFmpeg 解码，SDL 接收的是准备播放的音频数据。视频最终显示使用 Qt OpenGL，而不是 SDL 窗口。

## Q10：OpenGL 在项目中负责什么？

**回答：**

解码后的视频帧转换为可显示图像，通过 Qt signal 送到 `MyOpenGLWidget`。OpenGL 控件负责把图像绘制到窗口，并在控件尺寸变化时完成显示适配。

它的价值是把视频显示从普通 QLabel 绘制中独立出来，减少 CPU 缩放和重绘压力。当前实现仍可能存在图像拷贝，进一步优化可以直接上传 YUV 纹理并在 shader 中转换色彩。

## Q11：音视频同步怎么做？

**回答：**

当前播放器主要以音频时钟为参考。音频回调根据实际播放的数据推进 `audio_clock`；视频帧根据时间戳得到 `video_clock`，显示线程比较两个时钟，视频超前时等待，落后时减少等待。

选择音频作为主时钟是因为声卡播放不适合频繁加速或停顿，用户对音频断裂也更敏感。纯视频没有音频时，项目使用 SDL timer 控制帧显示节奏。

## Q12：PacketQueue 为什么需要 mutex 和 condition variable？

**回答：**

读取线程是生产者，音频回调和视频线程是消费者，它们并发访问队列。mutex 保证入队、出队和清空操作不会破坏链表状态；condition variable 让队列为空时消费者等待，新 packet 到达后被唤醒，而不是空循环占满 CPU。

停止和 seek 时还需要唤醒等待线程，并使用退出或 flush 标记改变消费者行为。队列不仅是数据容器，也是线程之间的节奏缓冲。

## Q13：seek 为什么比简单修改播放进度复杂？

**回答：**

FFmpeg seek 只是让读取位置跳转，音频队列、视频队列和解码器内部仍可能保存旧位置的数据。如果不清理，跳转后会继续播放旧帧，或者旧时间戳干扰同步。

项目由 UI 设置 seek 请求，读取线程执行 seek，清空队列并发送 flush 标记，音视频解码线程收到后刷新解码器状态，再从目标附近重新建立时钟。真实 seek 通常跳到关键帧附近，之后还可能丢弃关键帧到目标点之间的数据。

# 三、录制模块类

## Q14：VideoRecorder 的整体流程是什么？

**回答：**

`RecorderDialog` 组织录制参数和开始/停止操作。`PicInPic_Read` 采集桌面并合成摄像头画面，`Audio_Read` 用 `QAudioInput` 采集麦克风 PCM，两个数据源把帧交给 `SaveVideoFileThread`。

录制线程创建 FFmpeg 输出上下文，配置 H.264 视频编码和 AAC 音频编码，将编码 packet 按时间戳写入 FLV。停止时结束采集、刷新编码器、写 trailer 并释放文件资源。

## Q15：桌面画面如何采集？

**回答：**

当前实现通过 Qt 的屏幕 API获取主屏幕几何信息，并抓取桌面图像。图像再被转换成视频编码需要的格式和尺寸，送入视频队列。

这个方案实现简单，但高分辨率、多屏、高 DPI 和高帧率下效率有限。生产级 Windows 录屏可以使用 Desktop Duplication API 或 Windows Graphics Capture，减少桌面图像拷贝。

## Q16：摄像头画中画如何实现？

**回答：**

摄像头画面由 OpenCV 获取，桌面画面是主背景。`PicInPic_Read` 将摄像头帧缩放到指定区域，再覆盖到桌面图像上，最终把合成结果转换为 YUV 数据交给编码器。

这属于编码前图像合成。优点是输出文件中天然包含画中画；缺点是合成会消耗 CPU，且录制后不能单独关闭或移动摄像头层。

## Q17：麦克风音频如何采集？

**回答：**

项目使用 Qt Multimedia 的 `QAudioInput` 打开默认输入设备，按配置采集 PCM。采集到的原始音频进入录制模块，按 AAC 编码器需要的 sample format、sample rate、channel layout 和 frame size 组织。

设备实际支持格式可能与目标编码格式不同，因此完整实现需要重采样和格式转换。还要注意音频设备回调与编码线程之间的队列和生命周期。

## Q18：H.264/AAC 编码流程是什么？

**回答：**

先通过 `avcodec_find_encoder` 找编码器，创建 `AVCodecContext`，配置码率、分辨率、帧率、像素格式或音频采样参数，再 `avcodec_open2`。原始帧通过 `avcodec_send_frame` 送入编码器，循环 `avcodec_receive_packet` 获取压缩 packet。

packet 写入容器前要把编码器时间基转换到输出流时间基。结束时向编码器发送空帧进行 flush，取出延迟 packet，再写容器 trailer。

## Q19：录制时音视频时间戳为什么重要？

**回答：**

容器中的音频和视频是两条独立流，播放器依靠 PTS/DTS 和 time_base 决定播放顺序与同步。如果简单按“收到一帧就写一帧”而没有稳定时间戳，可能出现音画漂移、播放速度异常或 muxer 报错。

常见做法是视频按帧序号和帧率生成 PTS，音频按累计样本数生成 PTS，写包前执行时间基转换。长期录制还要处理采集设备时钟偏差。

# 四、网络通信类

## Q20：为什么使用 TCP，而不是 UDP？

**回答：**

媒体列表、文件上传和下载要求数据完整、有序，TCP 已经提供重传、排序、流量控制和拥塞控制，可以把重点放在应用层协议和文件状态上。

UDP 更适合能容忍丢包、强调实时性的场景，但需要额外实现序号、重传或前向纠错。当前项目并不是实时直播传输，所以 TCP 更合适。

## Q21：什么是 TCP 粘包和半包？

**回答：**

TCP 是字节流。半包是一次 recv 没有读到完整业务消息；粘包是一次 recv 包含多条业务消息的字节。它们不是 TCP 异常，而是应用层错误地假设了 recv 边界。

本项目用 4 字节长度头解决：先循环读满长度，再循环读满指定包体。下一轮重新读取下一条长度。

## Q22：为什么使用 4 字节长度头？

**回答：**

固定 4 字节容易先读取和解析，`int32_t` 能表示远大于当前需求的包长。项目另外限制最大 1 MB，避免恶意或损坏长度导致巨大内存分配。

长度头只负责分帧，包体第一个 `PackType` 再负责业务分发。这种“传输帧 + 业务包”分层简单清楚。

## Q23：网络接收线程为什么不能直接操作 Qt UI？

**回答：**

Qt 控件只能由 GUI 主线程安全访问。Winsock 接收循环运行在 `std::thread`，如果直接修改 QLabel 或 QTableWidget，可能出现竞争、随机崩溃或对象已经销毁。

项目让接收线程发出 QByteArray 信号，`AVNetworkClient` 解析后继续发出业务信号。Qt queued connection 将槽函数投递到 UI 对象所属线程。

## Q24：Windows 客户端和 Ubuntu 服务端通信要注意什么？

**回答：**

要注意整数大小、结构对齐、字节序、字符编码和 socket API 差异。当前使用固定宽度整数和 `#pragma pack(1)`，文件名按 UTF-8，Windows 用 Winsock，Linux 用 POSIX socket。

当前还有一个限制：整数直接按主机小端发送，没有标准序列化。两端都是 x86 时可用，但更通用的协议应使用网络字节序或 Protobuf 等明确编码，并加版本号。

## Q25：AVNetworkClient 和 TcpClient 为什么要分开？

**回答：**

`TcpClient` 只做连接、发送、接收和长度帧，不理解 Ping、列表或文件。`AVNetworkClient` 负责构造和解析 AV 业务协议，再向 UI 发出语义化信号。

这样新增业务包时不需要修改 socket 循环；更换底层网络实现时，页面和业务协议也不必全部重写。

## Q26：当前服务端是不是 epoll 高并发服务器？

**回答：**

不是。当前主线 `AVServer` 在 accept 一个客户端后同步执行 `handleClient()`，该连接断开后才继续 accept，属于阻塞式单连接最小实现。

原始 `NetDisk-Server` 有 epoll 和线程池参考，但尚未整合。面试中应主动说明这一点，并给出升级方案，而不是把目标架构说成已完成。

# 五、上传下载类

## Q27：上传为什么分 INIT、BLOCK、FINISH？

**回答：**

INIT 验证文件名、后缀和大小并创建 upload_id；BLOCK 按 offset 传输有限数据；FINISH 比较预期大小、累计大小和磁盘大小，再把临时文件提交到 media。

这个设计把“建任务、传数据、提交”分开，失败发生在哪一段很清楚，也为断点续传和哈希校验保留了位置。

## Q28：下载为什么也分 INIT、BLOCK、FINISH？

**回答：**

INIT 确认文件存在并获得总大小；BLOCK 让客户端按自身写盘速度请求数据；FINISH 复核服务端文件大小并形成完成日志。

客户端下载采用拉模型，一块写完再请求下一块，天然有背压。后续如果追求速度，可以从单块 ACK 扩展到滑动窗口。

## Q29：为什么使用 64 KB 分片？

**回答：**

64 KB 远低于 1 MB 包长上限，单块内存小，又比几 KB 小块减少大量往返。对局域网第一版来说，它在实现简单、进度粒度和传输效率之间比较均衡。

它不是固定最优值。高 RTT 环境中，串行 ACK 的吞吐上限约受 `block_size / RTT` 限制，应增加窗口或并发分片。

## Q30：为什么上传需要 temp 目录？

**回答：**

上传可能断线，直接写 `media/filename` 会让媒体列表看到半成品。服务端先写 `temp/<upload_id>.part`，只有 FINISH 校验成功才移动到 media。

temp 将“传输中”和“可用”状态隔离。它类似简化事务：rename 是提交点，失败任务可以单独清理。

## Q31：下载为什么先写 .part？

**回答：**

如果直接覆盖正式 cache 文件，断线会留下一个名字正常但内容残缺的文件，播放器可能误打开。`.part` 明确表示任务未完成，失败时删除，成功时检查大小后改名。

它还保护已有 cache：新下载完成前，旧正式文件理论上仍可使用。当前实现完成时替换同名 cache。

## Q32：如何避免路径穿越？

**回答：**

服务端不接受客户端完整路径，只接受基本文件名，并拒绝 `/`、`\` 和 `..`。最终路径只能由固定 `media/` 或 `temp/` 根目录与验证后的名字拼接。客户端创建 cache 前也再次验证服务端响应文件名。

更强的 Linux 实现可以使用 `openat`、目录 fd、`O_NOFOLLOW` 和规范化路径检查，防止符号链接竞态。

## Q33：如何处理上传同名文件？

**回答：**

服务端先检查目标名是否存在；存在时拆分 basename 和 suffix，依次尝试 `_1`、`_2`，并在 FINISH 响应中返回实际保存名。

当前服务端串行，所以检查与 rename 的竞争较小。多线程后必须使用原子创建、锁或数据库唯一约束，避免两个任务同时选到相同名字。

## Q34：为什么下载完成后再播放，不做边下边播？

**回答：**

完整下载后播放器面对普通本地文件，seek、文件尾索引、同步和错误处理全部复用。网络失败只影响下载，不会阻塞解码线程。

边下边播需要 FFmpeg 自定义 AVIOContext、缓存水位、阻塞 read、远程 seek、重连和缓存淘汰。它适合后续独立阶段，不应与最小文件传输同时引入。

# 六、工程与优化类

## Q35：为什么当前没有使用 MySQL？

**回答：**

当前需求只需要列出 `media/` 中的文件，目录扫描即可完成，部署也不依赖数据库账号、表结构和服务状态。先去掉 MySQL 能降低环境问题，突出 C/S 和音视频主线。

当需要用户归属、标签、分页、搜索、权限、配额或审计时，再引入数据库更合理。数据库保存元数据，实际大文件仍应留在文件系统或对象存储。

## Q36：当前项目主要不足是什么？

**回答：**

服务端是阻塞式单连接；协议依赖 packed struct 和主机字节序；没有认证、TLS、限速、哈希、取消、超时、重试和任务持久化；列表没有分页；播放器和录制器使用较旧 FFmpeg API；第三方依赖路径仍与本机目录结构关联。

这些不足可以按“协议基础、任务可靠性、服务端并发、业务能力、发布部署”分阶段优化，不应一次性重写。

## Q37：后续如何支持断点续传？

**回答：**

不仅要保留 offset，还要保存任务 ID、文件版本、临时路径和已完成范围。上传时服务端持久化任务并返回 resume offset；下载时客户端保留 `.part` 和元数据，重连后确认服务端文件仍是同一版本。

若支持乱序或并行块，还要记录 bitmap/range。恢复前必须通过大小、mtime 或 hash 防止把两个不同版本拼在一起。

## Q38：后续如何加入完整性校验？

**回答：**

INIT 可以携带整个文件 SHA-256，FINISH 时接收端重新计算并比较。为了断点和局部重传，还可以为每块增加 hash，快速定位损坏块。

MD5 适合作为教学项目的一致性检查，但安全性较弱；需要防恶意篡改时使用 SHA-256，并配合 TLS 或数字签名考虑传输真实性。

## Q39：如果并发用户增多，服务端怎么优化？

**回答：**

先将 accept/recv 改为 non-blocking socket + epoll，事件线程只负责网络状态；文件读取、写入和业务处理投递线程池。每个连接维护独立接收缓冲和发送队列，处理部分写，避免工作线程直接阻塞 epoll 线程。

`UploadManager` 的任务表和重名逻辑要加并发控制；同时增加连接数、任务数、速率和磁盘队列限制。大规模场景还应把元数据、文件存储和网关拆分。

## Q40：如何把它扩展为在线播放？

**回答：**

有两条路线。私有协议路线是实现分段缓存和自定义 AVIOContext，为 FFmpeg 提供 read/seek 回调；标准路线是服务端提供 HTTP Range、HLS 或 DASH，由 FFmpeg 使用成熟协议读取。

工程上更推荐先做 HTTP Range 或 HLS，因为播放器、CDN、缓存和 seek 语义更成熟。自定义 TCP 边下边播适合学习，但生产维护成本高。

## Q41：如何设计自动化测试？

**回答：**

协议层可以构造完整包、半包、粘包、非法长度、错误 data_size 和路径穿越文件名，验证解析和拒绝逻辑。文件传输可生成固定随机文件，上传下载后比较 SHA-256，并在不同 offset 主动断开连接。

UI 层做启动和关键页面冒烟；音视频层准备短小固定样本，验证能打开、总时长合理、录制文件可被 FFmpeg 探测。跨平台 CI 可分别构建 Windows 客户端和 Ubuntu 服务端。

## Q42：如果重新做一次，你会优先改什么？

**回答：**

我会先建立单一共享协议定义或代码生成，加入协议版本、网络字节序、request_id 和结构化错误码；然后将上传下载抽成统一 TransferTask 状态机，支持取消、超时和 hash。

服务端在功能稳定后接入 epoll + 线程池，而不是过早引入 MySQL。最后再统一第三方依赖和发布脚本。这条顺序能降低返工，并让每个阶段都有可演示结果。
