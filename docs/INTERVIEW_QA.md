# AVProject 面试问答复盘

## 使用方法

不要逐字背诵。建议每题按四层组织：

```text
先说结论
  -> 再说当前实现
  -> 再说设计取舍
  -> 最后说不足和优化
```

面试时必须区分“已经完成”和“计划优化”。当前主线 `AVServer` 已完成 non-blocking socket + epoll LT 单线程 Reactor，并接入核心 4、最大 8、队列 256 的有界动态业务线程池。MySQL、Argon2id 和 64 KB 文件 I/O 均在 worker，但仍是同步调用、固定参数和基础过载策略，不能描述成生产级高并发服务器。

# 一、项目整体类

## Q1：这个项目是做什么的？

**回答：**

这是一个 Windows 客户端加 Ubuntu 服务端的 C/S 音视频系统。Windows 端基于 Qt、FFmpeg、SDL、OpenGL 和 OpenCV，提供本地播放、桌面录制、远程媒体列表、分片上传和分片下载，并支持上传、下载断点续传；Ubuntu 端通过 TCP 自定义协议管理 `media/` 目录，处理列表、上传和下载。

当前完整闭环是：本地录制或选择媒体，上传到服务端，刷新远程媒体列表，再下载到客户端 cache，最后复用本地播放器播放。项目重点不是做商业视频平台，而是把音视频、网络、线程、文件传输和工程化组织串成一个可运行系统。

## Q2：为什么把播放器、录制器和 C/S 结合，而不是保留三个独立 Demo？

**回答：**

独立 Demo 只能证明单点 API 会用，整合项目还要解决模块边界、对象生命周期、线程通信、协议设计、跨平台构建和错误闭环。播放器输出消费能力，录制器产生媒体，C/S 模块让媒体可以远程管理，三者组合后才有真实业务流。

整合时我没有重写成熟的音视频核心，而是增加 Page 适配层、共享网络服务和协议管理器。这能说明我不仅能实现算法或 API，还能控制改动范围、复用已有模块并处理跨模块协作。

## Q3：项目的完整业务闭环是什么？

**回答：**

客户端可以录制桌面、摄像头和麦克风，生成本地 FLV；也可以选择其他本地媒体。Remote Media 页面将文件按 64 KB 分片上传，服务端先写 `temp/`，完整后移动到 `media/`。客户端刷新列表后选择远程文件，按 offset 分片下载到 `cache/*.part`，完成后改成正式文件，并调用本地播放器播放。

这个闭环覆盖“媒体产生、传输、服务端管理、获取和消费”。Ping 和媒体列表是控制面，上传下载是数据面，播放器和录制器是本地音视频能力。

## Q4：你在项目中具体完成了哪些工作？

**回答：**

可以按阶段回答：我先审查四个原始工程，保留播放器和录制器核心；然后创建统一 Qt Widgets 客户端，把播放、录制、远程媒体和设置页面整合进主窗口。之后实现 Windows Winsock 客户端、Ubuntu TCP 服务端和长度帧协议，再增加媒体列表、分片上传、分片下载以及下载后自动播放。

工程层面还包括相对依赖路径、DLL 部署脚本、运行目录隔离、`.gitignore`、阶段日志、架构和协议文档。回答时应明确哪些核心来自原始学习项目，哪些整合与网络功能是后续实现，避免把所有代码都说成从零编写。

## Q5：这个项目最关键的设计取舍是什么？

**回答：**

第一，优先打通最小闭环，不一开始整合 epoll、MySQL 和边下边播。第二，播放器与录制器采用薄适配复用，不重构音视频核心。第三，文件传输使用 64 KB 串行分片，牺牲极限吞吐换取简单状态和稳定 offset。第四，上传使用 temp，下载使用 `.part`，避免半成品进入正式目录。

这些取舍的共同原则是把风险拆开：先确认每个阶段可编译、可运行、可回归，再讨论并发和性能。

## Q6：当前项目最值得讲的工程能力是什么？

**回答：**

一是跨模块边界：UI、音视频工作线程、TCP 收包线程和文件系统各自负责明确职责。二是协议状态机：INIT、BLOCK、FINISH 让大文件传输有建立、推进和提交边界。三是失败语义：上传半成品留在 temp，下载半成品使用 `.part`，断线后不把它们当正式媒体。

另外，服务端从阻塞式单连接演进到 epoll 多连接后，仍明确记录同步磁盘 I/O 和单线程执行的边界。这种区分“并发 I/O”“并行业务处理”和“生产级高并发”的能力也属于工程判断。

# 二、播放模块类

## Q7：MediaPlayer 的整体播放流程是什么？

**回答：**

`PlayerDialog` 获取文件路径后调用 `VideoPlayer::setFileName()` 和 `start()`。`VideoPlayer` 继承 `QThread`，在线程中用 FFmpeg 打开输入、查找流、循环 `av_read_frame()`，把音频和视频 packet 分别放进两个 `PacketQueue`。

SDL 音频回调从音频队列取 packet、解码和重采样后送声卡；视频线程从视频队列取 packet、解码和转换图像，再通过 Qt signal 交给 OpenGL 控件显示。UI 线程只处理按钮、进度和图像展示，不执行持续解封装。

## Q8：FFmpeg 在播放模块里负责什么？

**回答：**

FFmpeg 负责输入协议和容器解析、流信息发现、音视频解码、时间戳以及格式转换。具体包括 `avformat_open_input`、`avformat_find_stream_info`、`av_read_frame`、解码器上下文、`swresample` 音频重采样和 `swscale` 图像格式转换。

FFmpeg 不直接负责 Qt 页面，也不直接负责声卡和最终 OpenGL 控件。项目把“媒体处理”与“设备输出/UI”分开。

## Q9：SDL 在项目中负责什么？

**回答：**

播放端 SDL 主要负责音频设备回调、线程/定时机制以及 packet 队列需要的 mutex 和 condition variable。音频设备主动拉取数据时触发回调，因此音频播放节奏由实际设备消费驱动。

SDL 不是解码器。压缩数据仍由 FFmpeg 解码，SDL 接收的是准备播放的音频数据。视频最终显示使用 Qt OpenGL，而不是 SDL 窗口。

## Q10：OpenGL 在项目中负责什么？

**回答：**

解码后的视频帧转换为可显示图像，通过 Qt signal 送到 `MyOpenGLWidget`。OpenGL 控件负责把图像绘制到窗口，并在控件尺寸变化时完成显示适配。

它的价值是把视频显示从普通 QLabel 绘制中独立出来，减少 CPU 缩放和重绘压力。当前实现仍可能存在图像拷贝，进一步优化可以直接上传 YUV 纹理并在 shader 中转换色彩。

## Q11：音视频同步怎么做？

**回答：**

当前播放器主要以音频时钟为参考。音频回调根据实际播放的数据推进 `audio_clock`；视频帧根据时间戳得到 `video_clock`，显示线程比较两个时钟，视频超前时等待，落后时减少等待。

选择音频作为主时钟是因为声卡播放不适合频繁加速或停顿，用户对音频断裂也更敏感。纯视频没有音频时，项目使用 SDL timer 控制帧显示节奏。

## Q12：PacketQueue 为什么需要 mutex 和 condition variable？

**回答：**

读取线程是生产者，音频回调和视频线程是消费者，它们并发访问队列。mutex 保证入队、出队和清空操作不会破坏链表状态；condition variable 让队列为空时消费者等待，新 packet 到达后被唤醒，而不是空循环占满 CPU。

停止和 seek 时还需要唤醒等待线程，并使用退出或 flush 标记改变消费者行为。队列不仅是数据容器，也是线程之间的节奏缓冲。

## Q13：seek 为什么比简单修改播放进度复杂？

**回答：**

FFmpeg seek 只是让读取位置跳转，音频队列、视频队列和解码器内部仍可能保存旧位置的数据。如果不清理，跳转后会继续播放旧帧，或者旧时间戳干扰同步。

项目由 UI 设置 seek 请求，读取线程执行 seek，清空队列并发送 flush 标记，音视频解码线程收到后刷新解码器状态，再从目标附近重新建立时钟。真实 seek 通常跳到关键帧附近，之后还可能丢弃关键帧到目标点之间的数据。

# 三、录制模块类

## Q14：VideoRecorder 的整体流程是什么？

**回答：**

`RecorderDialog` 组织录制参数和开始/停止操作。`PicInPic_Read` 采集桌面并合成摄像头画面，`Audio_Read` 用 `QAudioInput` 采集麦克风 PCM，两个数据源把帧交给 `SaveVideoFileThread`。

录制线程创建 FFmpeg 输出上下文，配置 H.264 视频编码和 AAC 音频编码，将编码 packet 按时间戳写入 FLV。停止时结束采集、刷新编码器、写 trailer 并释放文件资源。

## Q15：桌面画面如何采集？

**回答：**

当前实现通过 Qt 的屏幕 API获取主屏幕几何信息，并抓取桌面图像。图像再被转换成视频编码需要的格式和尺寸，送入视频队列。

这个方案实现简单，但高分辨率、多屏、高 DPI 和高帧率下效率有限。生产级 Windows 录屏可以使用 Desktop Duplication API 或 Windows Graphics Capture，减少桌面图像拷贝。

## Q16：摄像头画中画如何实现？

**回答：**

摄像头画面由 OpenCV 获取，桌面画面是主背景。`PicInPic_Read` 将摄像头帧缩放到指定区域，再覆盖到桌面图像上，最终把合成结果转换为 YUV 数据交给编码器。

这属于编码前图像合成。优点是输出文件中天然包含画中画；缺点是合成会消耗 CPU，且录制后不能单独关闭或移动摄像头层。

## Q17：麦克风音频如何采集？

**回答：**

项目使用 Qt Multimedia 的 `QAudioInput` 打开默认输入设备，按配置采集 PCM。采集到的原始音频进入录制模块，按 AAC 编码器需要的 sample format、sample rate、channel layout 和 frame size 组织。

设备实际支持格式可能与目标编码格式不同，因此完整实现需要重采样和格式转换。还要注意音频设备回调与编码线程之间的队列和生命周期。

## Q18：H.264/AAC 编码流程是什么？

**回答：**

先通过 `avcodec_find_encoder` 找编码器，创建 `AVCodecContext`，配置码率、分辨率、帧率、像素格式或音频采样参数，再 `avcodec_open2`。原始帧通过 `avcodec_send_frame` 送入编码器，循环 `avcodec_receive_packet` 获取压缩 packet。

packet 写入容器前要把编码器时间基转换到输出流时间基。结束时向编码器发送空帧进行 flush，取出延迟 packet，再写容器 trailer。

## Q19：录制时音视频时间戳为什么重要？

**回答：**

容器中的音频和视频是两条独立流，播放器依靠 PTS/DTS 和 time_base 决定播放顺序与同步。如果简单按“收到一帧就写一帧”而没有稳定时间戳，可能出现音画漂移、播放速度异常或 muxer 报错。

常见做法是视频按帧序号和帧率生成 PTS，音频按累计样本数生成 PTS，写包前执行时间基转换。长期录制还要处理采集设备时钟偏差。

# 四、网络通信类

## Q20：为什么使用 TCP，而不是 UDP？

**回答：**

媒体列表、文件上传和下载要求数据完整、有序，TCP 已经提供重传、排序、流量控制和拥塞控制，可以把重点放在应用层协议和文件状态上。

UDP 更适合能容忍丢包、强调实时性的场景，但需要额外实现序号、重传或前向纠错。当前项目并不是实时直播传输，所以 TCP 更合适。

## Q21：什么是 TCP 粘包和半包？

**回答：**

TCP 是字节流。半包是一次 recv 没有读到完整业务消息；粘包是一次 recv 包含多条业务消息的字节。它们不是 TCP 异常，而是应用层错误地假设了 recv 边界。

本项目用 4 字节长度头解决：先循环读满长度，再循环读满指定包体。下一轮重新读取下一条长度。

## Q22：为什么使用 4 字节长度头？

**回答：**

固定 4 字节容易先读取和解析，`int32_t` 能表示远大于当前需求的包长。阶段 7 服务端把包体限制为最大 256 KB，足以容纳 64 KB 数据块及协议头，也能避免恶意或损坏长度导致巨大内存分配。

长度头只负责分帧，包体第一个 `PackType` 再负责业务分发。这种“传输帧 + 业务包”分层简单清楚。

## Q23：网络接收线程为什么不能直接操作 Qt UI？

**回答：**

Qt 控件只能由 GUI 主线程安全访问。Winsock 接收循环运行在 `std::thread`，如果直接修改 QLabel 或 QTableWidget，可能出现竞争、随机崩溃或对象已经销毁。

项目让接收线程发出 QByteArray 信号，`AVNetworkClient` 解析后继续发出业务信号。Qt queued connection 将槽函数投递到 UI 对象所属线程。

## Q24：Windows 客户端和 Ubuntu 服务端通信要注意什么？

**回答：**

要注意整数大小、结构对齐、字节序、字符编码和 socket API 差异。当前使用固定宽度整数和 `#pragma pack(1)`，文件名按 UTF-8，Windows 用 Winsock，Linux 用 POSIX socket。

当前还有一个限制：整数直接按主机小端发送，没有标准序列化。两端都是 x86 时可用，但更通用的协议应使用网络字节序或 Protobuf 等明确编码，并加版本号。

## Q25：AVNetworkClient 和 TcpClient 为什么要分开？

**回答：**

`TcpClient` 只做连接、发送、接收和长度帧，不理解 Ping、列表或文件。`AVNetworkClient` 负责构造和解析 AV 业务协议，再向 UI 发出语义化信号。

这样新增业务包时不需要修改 socket 循环；更换底层网络实现时，页面和业务协议也不必全部重写。

## Q26：当前服务端是不是 epoll 高并发服务器？

**回答：**

当前主线已经使用 non-blocking socket + epoll LT，并通过单线程 Reactor 同时维护多个客户端，所以可以准确描述为“epoll 多客户端并发服务器”。每个 fd 有独立接收缓冲和发送队列，网络暂时不可读写不会阻塞其他连接。

阶段 10 把文件业务交给有界动态线程池，阶段 11 又把 MySQL 和 Argon2id 放入同一 worker 边界，不同连接可以并行执行业务。但它还不是生产级“高并发媒体服务器”：仍没有异步 I/O、系统化限流、任务优先级、工作窃取和正式压测数据。

# 五、上传下载类

## Q27：上传为什么分 INIT、BLOCK、FINISH？

**回答：**

INIT 验证文件名、后缀和大小并创建 transfer ID、resume token 与持久化任务；BLOCK 按 offset 传输有限数据并更新服务端确认偏移；FINISH 比较预期大小、累计大小和磁盘大小，再把临时文件提交到 media。

这个设计把“建任务、传数据、提交”分开，失败发生在哪一段很清楚，也为断点续传和哈希校验保留了位置。

## Q28：下载为什么也分 INIT、BLOCK、FINISH？

**回答：**

INIT 确认文件存在并获得总大小；BLOCK 让客户端按自身写盘速度请求数据；FINISH 复核服务端文件大小并形成完成日志。

客户端下载采用拉模型，一块写完再请求下一块，天然有背压。后续如果追求速度，可以从单块 ACK 扩展到滑动窗口。

## Q29：为什么使用 64 KB 分片？

**回答：**

64 KB 远低于服务端 256 KB 包体上限，单块内存小，又比几 KB 小块减少大量往返。对局域网第一版来说，它在实现简单、进度粒度和传输效率之间比较均衡。

它不是固定最优值。高 RTT 环境中，串行 ACK 的吞吐上限约受 `block_size / RTT` 限制，应增加窗口或并发分片。

## Q30：为什么上传需要 temp 目录？

**回答：**

上传可能断线，直接写 `media/filename` 会让媒体列表看到半成品。服务端先写 `temp/<transfer_id>.part`，任务元数据写到 `temp/tasks/<transfer_id>.task`，只有 FINISH 校验成功才移动到 media。

temp 将“传输中”和“可用”状态隔离。它类似简化事务：rename 是提交点，失败任务可以单独清理。

## Q31：下载为什么先写 .part？

**回答：**

如果直接覆盖正式 cache 文件，断线会留下一个名字正常但内容残缺的文件，播放器可能误打开。`.part` 明确表示任务未完成，失败时删除，成功时检查大小后改名。

它还保护已有 cache：新下载完成前，旧正式文件理论上仍可使用。当前实现完成时替换同名 cache。

## Q32：如何避免路径穿越？

**回答：**

服务端不接受客户端完整路径，只接受基本文件名，并拒绝 `/`、`\` 和 `..`。最终路径只能由固定 `media/` 或 `temp/` 根目录与验证后的名字拼接。客户端创建 cache 前也再次验证服务端响应文件名。

更强的 Linux 实现可以使用 `openat`、目录 fd、`O_NOFOLLOW` 和规范化路径检查，防止符号链接竞态。

## Q33：如何处理上传同名文件？

**回答：**

服务端先检查目标名是否存在；存在时拆分 basename 和 suffix，依次尝试 `_1`、`_2`，并在 FINISH 响应中返回实际保存名。

阶段 10 后多个 worker 可能并行业务，因此上传任务创建、最终命名和 rename 都处于 `UploadManager` 的同一把粗粒度 mutex 保护下，避免两个任务同时选到相同名字。这个方案容易验证正确性，但会降低多个上传任务之间的并行度；更高吞吐场景可改为原子创建、每任务锁或数据库唯一约束。

## Q34：为什么下载完成后再播放，不做边下边播？

**回答：**

完整下载后播放器面对普通本地文件，seek、文件尾索引、同步和错误处理全部复用。网络失败只影响下载，不会阻塞解码线程。

边下边播需要 FFmpeg 自定义 AVIOContext、缓存水位、阻塞 read、远程 seek、重连和缓存淘汰。它适合后续独立阶段，不应与最小文件传输同时引入。

# 六、工程与优化类

## Q35：为什么阶段 11 引入 MySQL，又为什么不把视频存进 MySQL？

**回答：**

前十个阶段只做单一公共目录，扫描文件足够。阶段 11 出现了用户名唯一性、密码哈希、媒体 owner、PUBLIC/MINE 和稳定 mediaId，这些是结构化关系数据，MySQL 的唯一索引、外键和条件查询更合适。

视频本体仍放文件系统。大 BLOB 会让数据库备份、复制和随机读取成本升高，也不利于现有 64 KB 文件传输；MySQL 只保存 owner、原名、唯一存储名、路径、大小和状态，兼顾业务查询与大文件 I/O。

## Q36：当前项目主要不足是什么？

**回答：**

服务端已支持 epoll、多客户端、有界动态线程池、MySQL 用户认证、媒体归属和上传任务文件持久化，但 worker 内仍使用同步文件 I/O，UploadManager 使用粗粒度锁；协议依赖 packed struct 和主机字节序；没有 TLS、长期 session、限速、强哈希、通用取消和自动重试；客户端上传和下载仍限制单活动任务；UI 没有复杂分页；播放器和录制器使用较旧 FFmpeg API。

这些不足可以按“协议基础、任务可靠性、服务端并发、业务能力、发布部署”分阶段优化，不应一次性重写。

## Q37：当前断点续传支持到什么程度？

**回答：**

当前已支持上传和下载断点续传。上传由客户端和服务端共同持久化任务，网络断开、AVClient 重启或 AVServer 重启后，用户重新登录并携带 transfer ID 和 resume token 请求恢复；服务端再校验 ownerUserId，并以 `.part` 实际安全大小返回 resume offset。

下载只在客户端保存 `.part`、mediaId 和任务 JSON，恢复前计算本地 safe offset；服务端按 mediaId 查询媒体并校验 size/mtime 后返回 accepted offset。服务端下载保持无状态，所以重启不需要加载下载任务。两类传输仍是严格连续的 64 KB 串行分片，没有 SHA-256、乱序分片、bitmap、多任务并行和通用取消。

## Q38：后续如何加入完整性校验？

**回答：**

INIT 可以携带整个文件 SHA-256，FINISH 时接收端重新计算并比较。为了断点和局部重传，还可以为每块增加 hash，快速定位损坏块。

MD5 适合作为教学项目的一致性检查，但安全性较弱；需要防恶意篡改时使用 SHA-256，并配合 TLS 或数字签名考虑传输真实性。

## Q39：如果并发用户增多，服务端怎么优化？

**回答：**

当前前两步已经完成：accept/recv/send 使用 non-blocking socket + epoll，每个连接维护独立收发状态；MySQL、Argon2id、文件读写和上传元数据投递到有界动态线程池。`completionQueue + eventfd` 把结果安全回投 Reactor，`connectionId` 防止 fd 复用导致陈旧响应或身份误投。

下一步不是继续堆线程，而是通过压测确定瓶颈，再增加连接数、任务数、速率和磁盘队列限制；还可细化 UploadManager 锁粒度、采用异步 I/O，并补充协议版本与鉴权。大规模场景才考虑拆分元数据、文件存储和接入层。

## Q40：如何把它扩展为在线播放？

**回答：**

有两条路线。私有协议路线是实现分段缓存和自定义 AVIOContext，为 FFmpeg 提供 read/seek 回调；标准路线是服务端提供 HTTP Range、HLS 或 DASH，由 FFmpeg 使用成熟协议读取。

工程上更推荐先做 HTTP Range 或 HLS，因为播放器、CDN、缓存和 seek 语义更成熟。自定义 TCP 边下边播适合学习，但生产维护成本高。

## Q41：如何设计自动化测试？

**回答：**

协议层可以构造完整包、半包、粘包、非法长度、错误 data_size 和路径穿越文件名，验证解析和拒绝逻辑。文件传输可生成固定随机文件，上传下载后比较 SHA-256，并在不同 offset 主动断开连接。

UI 层做启动和关键页面冒烟；音视频层准备短小固定样本，验证能打开、总时长合理、录制文件可被 FFmpeg 探测。跨平台 CI 可分别构建 Windows 客户端和 Ubuntu 服务端。

## Q42：如果重新做一次，你会优先改什么？

**回答：**

我会先建立单一共享协议定义或代码生成，加入协议版本、网络字节序、request_id 和结构化错误码；然后将上传下载抽成统一 TransferTask 状态机，支持取消、超时和 hash。

服务端已在功能稳定后完成 epoll Reactor，并在阶段 10 实现有界任务队列、`completionQueue + eventfd` 回投和 `connectionId` 生命周期保护。后续重点是统一复习调用链、补充压力数据和工程部署；若继续迭代，再考虑协议版本、SHA-256、鉴权和更细粒度并发控制，而不是直接引入大量基础设施。

## Q43：为什么当前选择 epoll LT，而不是 ET？

**回答：**

LT 在 fd 仍可读或可写时会继续通知，状态更容易验证；ET 只在状态变化时通知，要求每次一直读写到 `EAGAIN`，漏读可能让连接长期不再触发。当前实现即使使用 LT 也按“循环到 EAGAIN”编写，为以后评估 ET 保留基础，但阶段 7 优先降低调试成本。

## Q44：为什么每个连接必须有独立 receiveBuffer 和 sendQueue？

**回答：**

不同客户端到达速度和分帧位置完全独立：A 可能只有两个长度头字节，B 可能一次收到三帧。共享缓冲会混淆字节归属。发送侧也一样，某个慢客户端只应积压自己的响应，不能改变其他客户端的 offset 或阻塞它们。

## Q45：EPOLLOUT 为什么不能一直注册？

**回答：**

普通 socket 大部分时间都可写。如果永久监听 EPOLLOUT，`epoll_wait` 会不断返回这个 fd，造成无意义唤醒和 CPU 空转。项目只在发送出现 `EAGAIN` 且队列未清空时注册；全部发完后立即取消。

## Q46：epoll 是并发还是并行？

**回答：**

阶段 7 的单 Reactor 只提供 I/O 并发；阶段 10 加入业务线程池后，不同连接的数据库和文件操作可以在多个 worker 中并行。网络 I/O 仍由一个 Reactor 串行管理，而同一连接最多一个业务任务在途，所以同连接协议保持有序。

# 七、上传断点续传深入类

## Q47：断点偏移为什么必须由服务端决定？

**回答：**

客户端保存的 offset 只是它最后一次看到的 ACK，可能因为崩溃、缓存未刷新或状态文件损坏而过时；客户端也可能是恶意的。真正决定服务端已经可靠拥有多少字节的是服务端任务记录和 `.part` 实际大小。

恢复时服务端比较元数据 `received_size` 与磁盘文件大小，取较小的安全值。客户端必须 seek 到服务端返回的 `resume_offset`，不能要求服务端跳到自己的偏移。

## Q48：transfer ID 和 resume token 分别解决什么问题？

**回答：**

transfer ID 是任务定位键，类似公开任务编号；resume token 是恢复凭据，用来证明调用方持有创建任务时返回的秘密。只有 ID 没有 token，任何猜到编号的客户端都可能接管任务。

当前 token 优先从 `/dev/urandom` 读取 32 字节并编码为十六进制，失败时才回退 `std::random_device`。它不是用户权限，也没有 TLS 保护，不能替代登录鉴权和加密传输。

## Q49：为什么 fd 不能作为上传任务的永久身份？

**回答：**

fd 只在当前进程的一次连接生命周期内有效。客户端重连会获得新 fd；服务端重启后旧 fd 全部消失，数字还可能被内核复用给其他连接。因此 fd 不能持久化为任务所有者。

项目用 transfer ID + token 表示持久身份，用 `active_owner_connection_id` 表示当前会话绑定。连接断开只按 connectionId 解绑，任务仍可恢复；这个会话 ID 不写入任务元数据。

## Q50：为什么客户端和服务端都需要持久化状态？

**回答：**

服务端状态证明 `.part` 属于哪个任务、预期多大、已可靠写入多少；客户端状态保存原文件路径、服务器地址和恢复凭据。只有服务端持久化，AVClient 重启后找不到 token；只有客户端持久化，AVServer 重启后不知道 `.part` 是否可信。

两边恢复时再次握手，以服务端偏移为准，才能把“本地还知道源文件”和“远端还知道已收数据”重新接起来。

## Q51：元数据为什么先写临时文件再 rename？

**回答：**

直接覆盖任务文件时，如果进程在写到一半崩溃，原记录也被破坏。当前实现先完整写入 `.tmp`，调用 `fsync`，再用同目录 rename 覆盖正式文件；rename 在同一文件系统内提供原子名称切换，读者看到旧版本或新版本，而不是半个文件。

这仍不是完整数据库事务：当前没有显式 fsync 目录项，也没有跨多个文件的原子提交，但对小型单任务元数据已经显著降低半写风险。

## Q52：元数据大小和 `.part` 大小不一致怎么办？

**回答：**

恢复偏移取两者较小值。若 `.part` 比元数据大，超出的数据可能写入了文件但元数据还没可靠提交，服务端截断到较小值；若元数据比文件大，说明记录超前，更不能跳过缺失数据。修正会写日志并重新持久化。

这个策略偏保守，可能重传少量数据，但避免在文件中留下空洞或把未知数据当成已确认内容。

## Q53：为什么 offset 必须严格连续？

**回答：**

当前任务只保存一个 `received_size`，它表达 `[0, received_size)` 是连续有效区间。若允许跳跃写入，就必须额外保存区间集合或 bitmap，并在 FINISH 检查所有空洞，状态机复杂度会明显增加。

串行连续分片让恢复点唯一。重复的完整旧块不重写，只返回当前位置；向前跳跃或部分重叠直接拒绝。

## Q54：如何避免两个客户端同时恢复同一任务？

**回答：**

恢复首先校验 ID、token、文件名和大小，然后检查 `active_owner_connection_id`。任务已绑定另一条活动连接时返回 `task already active`；连接关闭后由 UploadManager 按 connectionId 统一解绑。

阶段 10 中多个 worker 会访问任务表，因此检查、绑定、分片写入、完成和解绑都由 UploadManager 的同一把 mutex 保护。connectionId 只表示当前会话，不持久化；永久恢复身份仍是 transfer ID 与 resume token。

## Q55：任务为什么要过期？

**回答：**

断点任务保留 `.part`，如果客户端永久不回来，磁盘会持续被占用。项目选择 72 小时 TTL：服务端启动时扫描一次，运行中每 5 分钟低频检查，删除超时且没有活动连接的 uploading 任务及元数据。

不在每次 `epoll_wait` 后扫描磁盘，是为了避免高频无效 I/O。当前 TTL 是常量，生产系统应按用户、文件大小和存储配额配置。

## Q56：为什么当前不能声称强内容一致性？

**回答：**

当前检查能发现任务 ID、token、文件名、大小、mtime、offset 和磁盘大小不匹配，但不能发现内容变化后大小和 mtime 恰好相同，也不能证明网络或磁盘上的每个字节与原文件完全一致。

强一致性需要至少在 FINISH 计算并比较 SHA-256。阶段 10 虽然已有业务线程池，但本阶段明确不加入哈希；后续可以把大文件哈希作为有界 worker 任务执行，再通过 completionQueue 安全回投 Reactor，同时评估它对普通传输任务的排队影响。

## Q57：每块都持久化元数据会有什么代价？

**回答：**

每 64 KB 分片都写小元数据、fsync 和 rename，可以让确认偏移非常可靠，但会增加磁盘同步次数，降低上传吞吐并占用 worker。当前 UploadManager 使用粗粒度 mutex，这段同步 I/O 还会让其他上传任务等待；阶段 8 至 10 优先验证恢复与并发状态正确性，因此接受这个代价。

后续可以每若干块或每隔固定时间批量刷新，但 ACK 语义必须随之调整：只能把已经达到所承诺持久化等级的偏移返回给客户端。

## Q58：上传断点续传和下载断点续传的主要区别是什么？

**回答：**

上传时权威半成品和写入偏移在服务端，服务端必须保护任务不被其他连接接管；下载时权威源文件在服务端，而半成品在客户端，客户端还要确认远端文件版本没有变化。

当前下载恢复保存服务端文件大小和 mtime，并在客户端保留 `.part` 与已写区间。恢复前取状态 offset 和 `.part` 实际大小的较小值，服务端确认版本未变后返回 accepted offset。该方案能发现常见变化，但不能发现同大小、同 mtime 的内容替换。

# 八、下载断点续传深入类

## Q59：下载断点续传的基本原理是什么？

**回答：**

下载中断时，不删除已经可靠写入的 `.part`，同时保存远程文件版本、服务器地址和确认偏移。重连后先确认远端仍是同一版文件，再从双方接受的非零 offset 继续请求数据。完成前始终使用临时后缀，只有总大小正确才改为正式 cache 文件。

## Q60：为什么下载服务端可以保持无状态？

**回答：**

每个下载块请求都携带 `mediaId + offset + request_size`。服务端按 mediaId 查询可信 stored name 后独立 open、seek、read，不需要保留跨请求文件游标。权威源文件已完整存在于 `media/`，未完成半成品在客户端，因此恢复状态自然由客户端保存。

这也意味着 AVServer 重启不会丢失下载会话：重启后重新 INIT、stat 文件并按 offset 读取即可。无状态减少了任务清理、token 和连接所有权问题。

## Q61：为什么不能只相信状态文件中的 confirmed offset？

**回答：**

状态写入和文件写入是两个动作，进程可能在两者之间崩溃，用户也可能手工移动或截断 `.part`。因此状态 offset 只是记录，真正可用数据还必须受 `.part` 实际大小约束。

项目取两者较小值。这样可能保守地重复下载少量尾部，但不会跳过本地根本不存在的字节。

## Q62：safe offset 是怎样计算和修正的？

**回答：**

基本公式是 `safe_offset = min(confirmed_offset, part_file_size)`。如果 `.part` 比 confirmed offset 大，说明尾部没有被状态确认，就截断到 confirmed offset；如果 `.part` 更小，则降低 confirmed offset 并更新状态。

还要检查 offset 非负且不超过 expected file size。`.part` 不存在时不能假装从记录偏移恢复，应提示任务不可恢复或让用户放弃后重新下载。

## Q63：accepted offset 为什么还要由服务端返回？

**回答：**

safe offset 是客户端根据本地状态提出的请求，服务端仍要确认远程文件版本和 offset 范围。`accepted_offset` 表示服务端明确同意的起点，客户端必须按它截断和 seek，不能只按自己的状态继续。

当前服务端在校验通过后原样接受请求偏移，但显式响应能形成清楚的握手边界，也为未来按块对齐、限额或版本策略预留空间。

## Q64：如何判断远程媒体在中断期间发生了变化？

**回答：**

初次 DOWNLOAD_INIT 返回文件大小和修改时间，客户端把它们持久化。恢复 INIT 再携带旧值，服务端重新 `stat()` 当前文件并逐项比较；不同就返回 `remote file changed`。

服务端不会静默从 0 开始，也不会让客户端继续拼接，因为两种行为都可能把旧半成品和新文件内容混在一起。

## Q65：为什么当前使用 size 和 mtime，而不直接计算 SHA-256？

**回答：**

size 和 mtime 获取成本低，只需一次 stat，能发现常见的替换、追加和截断。阶段 10 已有业务 worker，但大文件 SHA-256 会长期占用有限线程和磁盘带宽，可能让普通分片任务排队。

这是阶段性取舍，不是强一致性。后续可把 SHA-256 放入有配额的 worker 任务，或在媒体入库时预计算并维护稳定 ETag，再将结果通过 completionQueue 回投 Reactor。

## Q66：size 和 mtime 校验会漏掉什么情况？

**回答：**

如果内容被替换，但文件总大小相同，并且 mtime 被保留或碰巧相同，当前检测会认为版本未变。秒级 mtime 还可能在快速连续修改时发生碰撞。

因此项目只能说“防止大部分误恢复”，不能说“保证每个字节一致”。最终内容校验必须依赖密码学哈希。

## Q67：为什么下载恢复不需要 resume token？

**回答：**

上传 token 保护的是服务端可写半成品，避免其他客户端只猜 ID 就接管写入。下载不会修改远端文件，也没有服务端下载任务需要接管；当前连接本来就允许读取媒体列表中的文件，所以不需要额外 download token。

这不代表下载天然安全。未来媒体有用户归属时，应使用登录会话和权限校验控制读取，传输中还应加入 TLS。

## Q68：AVServer 重启后为什么不需要扫描下载任务？

**回答：**

服务端下载没有任务元数据。所有恢复所需信息都在客户端 JSON、客户端 `.part` 和服务端正式媒体文件中。重启后重新检查文件版本，按 accepted offset 读取即可。

与之相反，上传半成品位于服务端，因此 AVServer 重启必须扫描 `temp/tasks/` 并恢复任务映射。

## Q69：为什么下载完成前使用 `.part`，完成后再 rename？

**回答：**

`.part` 把半成品和正式文件隔离，避免播放器打开残缺媒体，也给恢复提供固定存储。下载完成后先检查实际大小，再改为正式文件名，这个 rename 就是客户端的提交边界。

如果重命名失败，不能删除任务并宣称成功；应保留 `.part` 和状态，供排查或重试。

## Q70：断线后为什么不自动无限重连和恢复？

**回答：**

自动策略还需要退避、上限、网络切换、服务器身份、用户取消和应用退出语义。阶段 9 以学习和可控测试为目标，断线后只保存状态并显示“等待恢复”，由用户连接正确服务器后手动恢复。

这种行为简单、可预测，也避免客户端在后台未经确认持续占用带宽。

## Q71：为什么一次只允许一个活动下载？

**回答：**

当前 RemoteMediaPage 只维护一组活动文件、offset、进度和响应状态。限制为一个任务可避免响应关联错误，并让上传、下载共享的忙状态容易理解。

多任务并行需要把每个传输抽成独立对象，引入 request ID、调度、带宽分配和多个文件句柄，不属于最小阶段范围。

## Q72：用户放弃下载时为什么不用发取消协议？

**回答：**

服务端下载是请求驱动且无状态的；客户端不再发送 BLOCK，服务器就没有持续任务可取消。放弃只需删除本地 JSON 和 `.part`。

若未来改成服务端主动推送、预读队列或后台转码，才需要显式 cancel 来释放服务端资源。

## Q73：如何为当前方案加入 SHA-256？

**回答：**

可以在媒体列表或 INIT 响应中返回服务端预先计算的 SHA-256，客户端下载完成后在工作线程计算本地文件哈希并比较。失败时保留或隔离文件，不能改成正式可播放状态。

若希望恢复时更精细地发现局部损坏，还可保存分片 hash；但哈希计算和磁盘读取应放在有界工作线程，避免阻塞 epoll Reactor 和 Qt UI。

# 九、动态业务线程池深入类

## Q74：进程和线程有什么区别？为什么 AVServer 选择进程内线程池？

**回答：**

进程拥有独立虚拟地址空间和系统资源边界，线程是进程内的执行流，同一进程的线程共享代码、堆和打开的文件描述符。进程隔离更强，但通信与切换成本通常更高；线程共享数据方便，但必须处理竞争、锁和生命周期。

AVServer 的业务任务需要复用同一份协议分发器、上传任务表和目录配置，使用进程内线程池可以低成本共享这些对象。当前项目规模不需要多进程隔离，因此选择“单 Reactor 线程 + 少量业务 worker”更容易理解和实现。

## Q75：已经有 epoll，为什么还需要线程池？

**回答：**

epoll 解决大量 socket 的就绪通知，但 MySQL、Argon2id、`pread/pwrite`、`fsync`、元数据更新和 rename 仍可能同步阻塞。如果这些工作在 Reactor 中执行，一个慢业务会推迟所有连接的 accept、recv 和 send。

线程池把这类业务与文件 I/O 移出 Reactor。Reactor 继续快速处理网络事件，不同连接的业务任务则可利用多个 worker 并行推进。

## Q76：Reactor 和 worker 的职责如何划分？

**回答：**

Reactor 独占 listen socket、`epoll_wait/epoll_ctl`、accept、非阻塞 recv/send、连接生命周期、收发缓冲区以及完成结果投递。worker 只处理已经复制好的协议包，调用 MediaManager、UploadManager 或 DownloadManager，并生成响应数据。

这个边界保证 socket 和 `ConnectionContext` 只有一个线程修改，避免为每个连接状态加大量锁。worker 不直接 send，也不持有连接对象裸指针。

## Q77：为什么不把 recv 和 send 也放进线程池？

**回答：**

非阻塞 socket 已经由 epoll 告知何时可读写，把它再投递到线程池会增加任务切换、锁竞争和顺序协调。多个 worker 同时操作同一 socket 还会使收发缓冲区、部分写和关闭流程变得复杂。

当前设计让 Reactor 统一拥有网络 I/O，worker 专注可能阻塞的业务。这正是 Reactor 模式常见的职责分离。

## Q78：什么是生产者—消费者模型？本项目如何体现？

**回答：**

生产者生成任务并放入共享队列，消费者从队列取出任务执行。这里 Reactor 是生产者：解析完整业务包后调用 `submit()`；worker 是消费者：等待任务、取出并执行，再把结果放入 completionQueue。

任务队列由 mutex 保护，condition variable 负责在新任务到达或线程池停止时唤醒 worker。有界队列还给生产速度和消费能力之间建立了明确边界。

## Q79：condition_variable 如何避免忙等？

**回答：**

没有任务时，worker 在持有 `unique_lock` 的条件下调用 `wait()` 或 `wait_for()`。等待会原子地释放 mutex 并让线程休眠，不会不断循环检查队列消耗 CPU；被通知后重新获得锁并再次检查条件。

核心线程使用持续等待，非核心线程使用带 60 秒超时的等待。所有判断都使用谓词或循环，应对虚假唤醒。

## Q80：任务队列为什么既要加锁又要有上限？

**回答：**

多个提交者和 worker 可能同时访问队列，不加锁会破坏容器内部结构或丢失任务。上限则用于过载保护：如果生产速度长期大于消费速度，无界队列会持续占用内存，并让请求延迟失去上限。

当前容量固定为 256。满载时 `submit()` 返回 false，Reactor 清除 in-flight 并回复 `server busy`，让压力显式反馈给客户端。

## Q81：核心线程和非核心线程有什么区别？

**回答：**

核心线程是服务启动时创建并长期保留的基础处理能力，本项目固定为 4 个；即使空闲也不会因超时退出。非核心线程是在任务积压时临时增加的弹性容量，最多把总数扩到 8 个，连续空闲 60 秒后可退出。

两类线程执行任务的逻辑相同，区别主要是创建时机和空闲退出策略。

## Q82：动态线程池如何扩容，又如何保证不超过最大值？

**回答：**

每次提交先把任务加入队列，然后在同一把线程池 mutex 下比较“待处理任务数是否大于空闲 worker 数”和“当前 worker 数是否小于 8”。同时满足时只新增一个非核心 worker。

线程总数检查与创建记录都在锁保护区内，因此即使多个线程连续 submit，也不能同时看到过期计数而突破最大值。单次只扩一个还可避免瞬间创建过多线程。

## Q83：动态线程池如何缩容，又如何保证不低于核心数？

**回答：**

非核心 worker 在没有任务时调用 `wait_for(60s)`。超时后再次在锁内确认队列仍为空、线程池未停止且当前线程总数大于核心数，才把自己标记完成并退出。

核心 worker 不走空闲超时退出分支，因此至少保留 4 个。判断和计数更新在同一把锁内，多个非核心线程同时超时时也不会把总数减到核心数以下。

## Q84：为什么不能强制终止正在执行任务的线程？

**回答：**

线程可能正持有 mutex、写 `.part`、更新元数据或执行 rename。强制终止会让锁永远不释放，也可能留下半写文件和不一致任务状态。C++ 标准线程也没有安全的通用强杀接口。

本项目只让空闲非核心线程自然退出；停止服务时不再接收新任务，已入队任务执行完成后，worker 从循环返回并由拥有者 join。

## Q85：空闲线程数和线程总数怎样维护？

**回答：**

`currentThreadCount` 和 `idleThreadCount` 都只在线程池 mutex 保护下读写。worker 创建并进入等待态时计入空闲，取到任务前减少空闲，任务结束后重新增加；退出前同步减少对应计数。

这些计数用于扩容判断和日志观测，不应脱离锁单独读取，否则 submit 可能根据互相矛盾的快照错误扩容。

## Q86：动态 worker 退出后，对应的 std::thread 如何回收？

**回答：**

每个 worker 对象保存 id、是否核心、`std::thread` 和 `finished` 标志。非核心线程退出前设置 finished；后续 submit 调用 `reapFinishedWorkers()`，把已完成且可 join 的对象移出共享容器，再在锁外 join，避免持锁等待。

服务停止时统一取出剩余 worker 并 join。线程不会 join 自己，也不使用 detach，因此不会累积已退出但仍 joinable 的线程对象。

## Q87：eventfd 是什么？为什么适合唤醒 Reactor？

**回答：**

`eventfd` 是 Linux 提供的计数型文件描述符。其他线程写入一个 64 位整数后，它会变为可读，因此可以像 socket 一样注册到 epoll；Reactor 读出计数后批量处理完成队列。

它比轮询 completionQueue 更及时，也不需要为每个任务创建管道或 fd。项目全局只使用一个 non-blocking、close-on-exec 的 eventfd。

## Q88：completionQueue 为什么必须单独加锁？

**回答：**

多个 worker 可能同时完成任务并 push，而 Reactor 同时会批量取出结果。`std::queue` 本身不是线程安全容器，不加锁会产生数据竞争。

worker 在短临界区内 push 后立刻解锁，再写 eventfd；Reactor 被唤醒后在锁内把队列交换到局部容器，随后在锁外投递响应，从而缩短共享锁占用时间。

## Q89：为什么工作线程不能直接调用 send？

**回答：**

non-blocking send 可能只写出部分数据或返回 EAGAIN，需要修改该连接的发送偏移、sendQueue 和 EPOLLOUT 监听状态。如果 worker 直接 send，就会与 Reactor 并发修改同一连接，并引入关闭竞态和乱序。

当前 worker 只生成响应，Reactor 按连接顺序加入 sendQueue 并完成实际发送，网络状态始终由单一线程拥有。

## Q90：fd 为什么会复用？只保存 fd 有什么风险？

**回答：**

fd 是进程内文件描述符表的槽位。连接关闭后数字会被释放，下一次 accept 很可能再次得到相同数字。如果旧 worker 只携带 fd，它完成时可能把旧响应发送给恰好复用该 fd 的新客户端。

所以 fd 只用于日志和当前 Reactor 查找，不能作为跨异步任务的唯一身份。

## Q91：connectionId 如何避免陈旧任务响应？

**回答：**

每次 accept 都分配一个单调递增的 64 位 connectionId，并建立 connectionId 到 fd 的映射。worker 捕获的是 ID 和协议包副本；完成后 Reactor 先确认该 ID 仍存在，并确认当前 context 的 ID 一致，再投递响应。

旧连接关闭时映射被删除。即使 fd 被复用，新连接也有不同 ID，旧 completion 会被识别为陈旧结果并丢弃。

## Q92：为什么每个连接最多一个在途业务任务？

**回答：**

上传协议依赖 INIT、连续 BLOCK 和 FINISH 的严格顺序。如果同一连接的多个包并行进入不同 worker，后一个分片可能先写入，offset 检查就会失败，响应顺序也可能变化。

`businessTaskInFlight` 把每连接业务串行化：可以继续 recv 并缓存字节，但当前 completion 返回前不再分发后续业务包。不同连接仍可并行，设计简单且适合当前客户端单任务模型。

## Q93：每连接一个在途任务有什么不足？

**回答：**

同一连接上的轻量请求会被前面的慢任务阻塞。例如 Argon2id 或数据库查询未完成时，该连接后续列表或分片不能提前执行。它也没有 request ID，无法支持一个连接上的多任务乱序完成。

若未来需要多路复用，应给请求增加唯一 ID、建立每任务状态机并定义顺序或依赖规则；当前阶段用串行约束换取正确性和易理解性。

## Q94：UploadManager 为什么需要 mutex？粗粒度锁有什么取舍？

**回答：**

加入 worker 后，不同连接可能同时创建、恢复、写入、完成或清理上传任务。任务表、活动所有者、received offset、重名选择和元数据文件之间存在组合不变量，必须同步保护。

当前用一把 mutex 覆盖整个 UploadManager 公共操作，容易证明状态一致，也避免返回内部裸指针。代价是某个上传执行 64 KB 写盘、fsync 和元数据 rename 时，其他上传可能等待，降低并行度；这是学习阶段有意选择的正确性优先方案。

## Q95：MediaRepository 和 DownloadManager 为什么不共享全局文件游标？

**回答：**

MediaRepository 每次从连接池独占借用一个 `MYSQL*`，Prepared Statement 也只属于当前调用；DownloadManager 根据数据库查出的可信 stored name 和 `offset + size` 每次独立打开正式文件，不保存全局下载任务和共享 seek 位置。因此无需用一把全局 mutex 串行化所有列表和下载。

它们仍要做路径安全、普通文件检查、长度上限和文件变化检查。无共享业务状态不等于无需输入校验。

## Q96：客户端在 worker 执行期间断开会怎样？

**回答：**

Reactor 立即从 epoll 和两张连接映射中删除该连接，关闭 socket，并按 connectionId 通知 UploadManager 解除活动绑定。已经开始的 worker 不被强杀，它可以把当前 64 KB 写盘或读取完成。

结果进入 completionQueue 后，Reactor 找不到原 connectionId，便丢弃响应。若上传块已经可靠写盘，客户端下次恢复时由服务端权威 offset 接着传，不需要回滚成功数据。

## Q97：线程池如何安全停止？

**回答：**

服务器先退出事件循环并停止接收新连接，然后 `ThreadPool::stop()` 把 stopping 置真、拒绝新 submit 并唤醒所有 worker。当前策略会继续执行已经入队的任务，队列排空后线程退出，拥有者逐个 join。

线程池完全停止后，服务器再清理完成结果、客户端 socket、eventfd 和 epoll fd。整个过程不 detach、不强杀任务，也避免 worker 在 eventfd 已关闭后回投。

## Q98：动态线程数应该如何配置？当前方案还有哪些不足？

**回答：**

线程数取决于 CPU 核数、任务中阻塞 I/O 的比例、磁盘并发能力、内存和期望延迟。当前固定 4 至 8 是便于学习和测试的保守参数，不是通过正式压测得出的最优值；队列 256 和 60 秒超时同样需要结合负载验证。

当前方案没有任务优先级、工作窃取、按磁盘类型分池、每用户公平性、运行时配置、细粒度指标或生产级自适应算法。项目应准确描述为“完成了有界动态线程池和安全回投闭环”，而不是通用高性能调度框架。

# 十、MySQL 认证与媒体归属类

## Q99：为什么所有 worker 不能共用一个 MYSQL 指针？

**回答：** 同一 MySQL 连接包含当前协议状态、结果集和错误信息，多线程并发操作会互相覆盖并产生竞态。本项目建立固定连接池，一个 lease 在同一时刻只交给一个 worker；连接归还后才可被其他任务复用。Statement 也在当前连接上按调用创建和销毁，不跨线程共享。

## Q100：为什么不在每次登录时新建数据库连接？

**回答：** TCP 握手、MySQL 鉴权和字符集初始化都有延迟，高并发下频繁连接还会增加数据库线程和端口压力。固定池把连接成本放到服务启动阶段，worker 只做有限等待的借还；默认 4 个连接也能给数据库并发设置清晰上限。

## Q101：Prepared Statement 如何降低 SQL 注入风险？

**回答：** SQL 模板先编译，用户名、关键字等随后作为带长度和类型的参数绑定。数据库不会把参数中的引号、注释符重新解释为 SQL 语法，因此 `' OR 1=1 --` 只是一个普通用户名。它不能替代长度、编码和权限检查，但消除了最典型的字符串拼接注入入口。

## Q102：为什么密码使用 Argon2id，而不是 MD5 或 SHA-256？

**回答：** MD5 和普通 SHA-256 计算太快，攻击者拿到数据库后可以用 GPU 大规模穷举。Argon2id 是专门的密码哈希，具有随机盐、可调时间成本和内存成本。libsodium 生成的完整字符串包含算法、参数、盐和哈希，登录时可直接交给 verify，不需要自己设计盐格式。

## Q103：随机盐是否需要保密？

**回答：** 盐不需要保密，它的作用是让相同密码产生不同哈希，阻止彩虹表和批量复用计算。真正必须保密的是原始密码。当前 libsodium 把盐编码在 hash 字符串中，数据库只保存这个字符串即可。

## Q104：Argon2id 已经安全，为什么还需要 TLS？

**回答：** Argon2id 保护的是数据库泄露后的离线破解风险；客户端到服务端之间仍发送原始密码。没有 TLS，同网段监听者可能直接看到密码和 resume token。客户端先发 MD5 也不解决问题，因为固定摘要会变成可重放凭据。公网部署必须加入 TLS 和服务器身份校验。

## Q105：为什么登录必须在线程池执行？

**回答：** MySQL 查询可能等待网络或连接池，Argon2id 故意消耗 CPU 和内存。若放在单 Reactor 线程，某次慢登录会拖住所有连接的 accept、recv、send 和 Ping。当前 Reactor 只组帧和提交任务，worker 完成查询与验证后通过 completionQueue/eventfd 回投。

## Q106：worker 为什么不能直接修改 ConnectionContext？

**回答：** ConnectionContext 的创建、销毁和 fd 映射都由 Reactor 管理。worker 执行期间客户端可能断开，指针会悬空，fd 也可能被新连接复用。worker 只返回 userId/username 值；Reactor 按不可复用的 connectionId 重新查找，连接仍存在才更新身份。

## Q107：客户端保存的 userId 为什么不可信？

**回答：** 客户端进程和网络包都能被修改。如果上传请求携带 userId 并被服务端直接信任，攻击者只需改成别人的 ID。当前媒体业务包不包含授权 userId，服务端从已经登录的 ConnectionContext 读取，并把这个快照交给 worker。

## Q108：ownerUserId 和 activeOwnerConnectionId 有什么区别？

**回答：** ownerUserId 是数据库用户的长期业务身份，会写入 `.task`，断线和服务端重启后仍有效。activeOwnerConnectionId 只是当前进程内的排他会话绑定，连接关闭就清零，不持久化。前者解决“任务属于谁”，后者解决“现在谁正在写”。

## Q109：其他用户拿到 transferId 和 token 后为什么仍不能恢复？

**回答：** RESUME 先定位任务并恒定时间比较 token，再比较任务 ownerUserId 与当前可信登录 userId，还会校验文件名和大小。任一条件失败都不绑定连接、不修改 offset、不破坏 `.part`。因此 token 是必要条件但不再是唯一授权条件。

## Q110：旧 `.task` 没有 owner 字段怎么办？

**回答：** 启动加载时把它识别为 legacy owner 0，记录日志但不崩溃；认证模式下拒绝恢复。不能在第一次恢复时偷偷绑定当前用户，因为系统没有证据证明历史文件属于谁，这会制造越权归属。

## Q111：original_name 和 stored_name 为什么要分开？

**回答：** original_name 用于 UI，保留用户看到的中文或业务文件名；stored_name 使用 transferId 加扩展名，是服务器内部唯一磁盘标识。两个用户都上传 `test.mp4` 时展示名可以相同，但物理路径不冲突，下载也通过 mediaId 定位而不是猜文件名。

## Q112：上传完成时如何处理文件与数据库的一致性？

**回答：** FINISH 先确认 `.part` 大小，再 rename 为正式 stored name，随后插入 media 记录。只有两步都成功才返回上传成功并删除 `.task`。若 INSERT 失败，服务端尝试把正式文件 rename 回 `.part`，保留任务供客户端稍后重新 FINISH。它是简单补偿，不是跨文件系统和 MySQL 的真正原子事务。

## Q113：PUBLIC 和 MINE 如何实现？

**回答：** 两者都只查询 `status='published'`。PUBLIC 不限制 owner；MINE 额外绑定 `owner_user_id=?`，参数来自 ConnectionContext 的 userId。查询还使用 page、pageSize、keyword 参数，当前 UI 为降低复杂度固定第一页 100 条和空关键字。

## Q114：为什么下载改用 mediaId？

**回答：** 原始文件名可能重名、改名，也不应该决定服务器内部路径。mediaId 是数据库稳定主键，服务端可由它查询 published 状态、owner、stored name 和 storage path。客户端从不发送 storage_path，避免把路径选择权交给不可信输入。

## Q115：按 mediaId 后下载为什么仍可保持服务端无状态？

**回答：** 每个 INIT/BLOCK/FINISH 都可以用 mediaId 重新查询当前媒体记录，再用请求 offset 独立读取文件。服务端不需要保存 downloadId、文件游标或恢复 token；客户端持久化 mediaId、size、mtime、safe offset 和 `.part` 即可。代价是每块多一次简单数据库查询，当前学习项目接受这个取舍。

## Q116：数据库连接池大小为什么不等于最大 worker 数？

**回答：** worker 不只做数据库任务，还做文件 I/O；让 8 个 worker 都长期占一个数据库连接会扩大数据库压力。默认 4 个池连接接近核心线程数，其他任务最多等待 2.5 秒，超时返回 DATABASE_UNAVAILABLE。实际生产值应根据查询延迟、数据库容量和压测调整。

## Q117：MySQL 暂停后为什么 Ping 仍应响应？

**回答：** Ping 不访问数据库，并在 Reactor 中直接生成响应。登录、列表和媒体操作在 worker 内等待连接或重连，连接池等待有上限，因此数据库故障不会把 Reactor 事件循环一起阻塞。若所有 worker 暂时被占用，有界队列还会以 SERVER_BUSY 做过载保护。

## Q118：阶段 11 认证还存在哪些安全缺口？

**回答：** 最大缺口是没有 TLS，密码和 token 可能被监听；其次没有长期 session、登录限速、锁定策略、审计、角色、私有媒体权限和密钥轮换。size/mtime 也不是强内容完整性证明。项目应描述为局域网教学用最小认证闭环，而不是可直接公网运营的账号系统。
