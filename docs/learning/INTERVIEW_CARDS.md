## 面试知识卡 01：项目总体架构

### 1. 一句话说明模块作用

AVProject 是一个将本地音视频播放、录制和远程媒体分片传输整合起来的 C/S 系统：Windows Qt 客户端负责交互与本地媒体处理，Linux 服务端负责多连接网络 I/O、共享媒体目录和可恢复文件传输。

### 2. 一条完整业务流程

```text
用户在 Qt 页面发起远程媒体操作
→ AVNetworkClient 组装业务协议
→ TcpClient 添加长度头并通过 TCP 发送
→ EpollServer Reactor 非阻塞接收并增量拆包
→ 文件类请求提交动态线程池
→ ProtocolDispatcher 调用 MediaManager / UploadManager / DownloadManager
→ worker 生成 CompletedTask 并写入 completion queue
→ eventfd 唤醒 Reactor
→ Reactor 校验 connectionId、加入发送队列并处理部分发送
→ 客户端接收线程读取完整响应
→ AVNetworkClient 分发 Qt 信号
→ 页面更新列表、传输进度或调用本地播放器
```

本地播放和录制不经过服务端；下载并播放是完整下载到 `cache/` 后复用本地播放器。

### 3. 三个核心技术点

1. 客户端按需线程模型：Qt GUI 主线程配合 TCP 接收线程、播放器解封装/SDL 音视频线程、录制采集/编码线程。
2. 服务端 epoll LT 单线程 Reactor + 4～8 worker 的有界动态线程池，网络 I/O 与同步文件业务分工。
3. completion queue + eventfd 把 worker 结果安全交还 Reactor，并用 connectionId 过滤连接关闭和 fd 复用后的陈旧结果。

### 4. 采用当前方案的三个原因

1. **采用方案：播放和录制都在客户端本地完成。**采用原因：显示器、声卡、摄像头和桌面采集源都位于用户机器，本地处理能避免持续传输原始音视频，降低网络带宽、延迟和服务端计算压力。
2. **采用方案：服务端使用 epoll LT 单线程 Reactor 管理网络，数据库与文件业务交给动态线程池。**采用原因：Reactor 适合集中维护多个非阻塞 socket、连接和认证状态，worker 隔离 MySQL、Argon2id 和同步文件 I/O，避免一次慢业务拖住全部客户端。
3. **采用方案：远程媒体完整下载到本地缓存后，复用现有播放器播放。**采用原因：下载与播放职责清晰，无需实现 FFmpeg 自定义 AVIO、缓存水位和边下边播同步，断点任务也更容易按完整文件管理。

### 5. 两个替代方案及比较

1. 每连接一线程：实现直观，但连接增多会增加线程栈、调度和上下文切换；当前 Reactor 更适合大量空闲或间歇活跃连接。
2. HTTP/HTTPS + 对象存储/HLS：生态、鉴权、代理和可移植性更成熟，也能支持流式播放；当前自定义 TCP 更适合展示长度帧、拆包、状态机和 epoll 学习成果，但生产化能力较弱。

### 6. 三个异常场景

1. 传输中断线：客户端保存未完成任务；上传服务端保留 `.part/.task`，下载客户端保留本地 `.part`。
2. worker 完成时原连接已关闭：Reactor 用 connectionId 检查，找不到或与当前连接不匹配就丢弃 CompletedTask。
3. 偏移或文件身份不一致：上传拒绝非期望 offset；下载恢复比较文件大小和修改时间，远程文件变化时拒绝继续追加。

### 7. 当前实现的不足

- 已有 MySQL + Argon2id 最小认证和媒体 owner，但没有 TLS、长期 session 和复杂权限。
- 下载完成后才能播放，不支持边下边播、HLS/RTMP 或服务端转码。
- 没有 SHA-256 等强内容校验和数据库媒体索引。
- 客户端部分同步发送和本地 `QFile` I/O 位于 GUI 线程。
- 部分跨线程标志、线程等待超时和录制资源所有权不够严格。
- 线程池扩缩容、任务治理、监控和锁粒度仍是教学型实现。

### 8. 30 秒回答

这是一个基于 Qt、FFmpeg 和 Linux 网络编程的 C/S 音视频项目。Windows 客户端支持本地播放、桌面摄像头麦克风录制、远程媒体列表和分片上传下载；Linux 服务端使用 epoll LT 单线程 Reactor 管理多客户端，把文件业务交给 4～8 个动态 worker，再通过 completion queue 和 eventfd 把结果交回 Reactor。项目实现了双向断点续传，其中上传由服务端持久化任务，下载主要由客户端保存恢复状态。

### 9. 2 分钟回答

AVProject 由 Windows Qt 客户端和 Linux 服务端组成。客户端有 Player、Recorder、Remote Media 和 Settings 四个页面，共享一个 AVNetworkClient。播放器使用 FFmpeg 解封装和解码，SDL 输出音频，OpenGL 显示视频；录制器采集桌面、摄像头和麦克风，把视频编码成 H.264、音频编码成 AAC，最后封装为 FLV。本地播放和录制不依赖服务器。

远程媒体功能使用自定义 TCP 二进制协议。客户端 TcpClient 使用长度头发送和接收完整包；服务端采用非阻塞 socket 和 epoll LT 单线程 Reactor，每个 ConnectionContext 保存独立收发状态和认证身份。Reactor 只负责 accept、recv、增量拆包、部分发送、连接生命周期和认证更新，MySQL、Argon2id、媒体查询与文件 I/O 交给有界动态线程池。worker 不直接 send，也不持有 ConnectionContext，而是生成 CompletedTask 并通过 eventfd 唤醒 Reactor；Reactor 用 connectionId 检查原连接仍有效，避免 fd 复用导致旧响应或身份误投。

文件传输按 64 KB 串行分块。上传由客户端和服务端共同保存任务，服务端以 `.part` 实际大小确认恢复偏移；下载服务端按文件名和 offset 无状态读取，客户端保存 `.part`、文件大小和修改时间。当前边界是没有真实鉴权、强哈希、边下边播和生产级任务治理，部分客户端文件 I/O 仍可能阻塞 GUI。

### 10. 五个常见追问及参考答案

1. **问：为什么上传服务端需要保存状态，而下载服务端可以基本无状态？**  
   **答：**上传过程中，服务端正在形成一个尚不完整的新文件，需要记录 transferId、resumeToken、目标文件名、期望大小和已接收偏移，并把 `.task` 与 `.part` 持久化，才能在断线或服务端重启后恢复。下载的数据源已经是 `media/` 中的完整文件，客户端每次携带文件名、offset 和请求大小，服务端校验文件大小、修改时间后即可读取，因此不需要长期保存下载会话；恢复状态主要由客户端 `DownloadTaskStore` 保存。

2. **问：为什么 worker 不能直接操作 `ConnectionContext` 或调用 `send`？**  
   **答：**`ConnectionContext`、发送队列和 epoll 事件由 Reactor 单线程独占。如果 worker 直接访问，连接可能在任务执行期间关闭，形成悬空指针；多个 worker 并发发送还会破坏响应顺序并增加锁竞争。当前 worker 只处理 packet 副本并生成 `CompletedTask`，由 Reactor 校验 connectionId 后统一入发送队列和处理部分发送。

3. **问：eventfd 与 completion queue 分别负责什么？**  
   **答：**completion queue 保存完整的业务完成结果，包括 connectionId、协议类型和响应包；eventfd 不承载这些业务数据，只负责通知并唤醒阻塞在 `epoll_wait` 的 Reactor。可以概括为“队列传数据，eventfd 发通知”。

4. **问：fd 已经能找到连接，为什么还需要 connectionId？**  
   **答：**fd 是内核可复用的整数。旧连接关闭后，新连接可能获得相同 fd；此时旧 worker 的完成结果若只按 fd 投递，就可能发给新客户端。项目为每次 accept 分配新的 connectionId，完成时同时检查连接身份，旧 connectionId 不存在或不匹配就丢弃响应。

5. **问：如果改成生产系统，你会优先优化哪三项，为什么？**  
   **答：**第一，加入 TLS、真实认证、权限和路径安全治理，先解决数据泄露与越权风险；第二，把客户端同步文件 I/O 和发送移出 GUI 线程，并为服务端增加任务超时、取消、监控和背压，提升可用性；第三，增加 SHA-256 等强完整性校验、原子文件状态和更可靠的任务存储，保证断点续传在崩溃与文件变化下的一致性。若产品需要低首帧延迟，再进一步采用 HTTP/HLS、对象存储或自定义 AVIO 支持边下边播。

## 面试知识卡 02：音视频播放器

### 1. 一句话说明模块作用

播放器模块从本地文件或网络 URL 解封装出音视频 Packet，分别完成解码、格式转换、音视频同步，并通过 SDL 输出 PCM、通过 Qt/OpenGL 显示视频。

### 2. 一条完整业务流程

```text
PlayerDialog::playLocalFile / 打开 URL
→ VideoPlayer::setFileName
→ QThread::start
→ VideoPlayer::run
→ avformat_open_input 打开输入
→ avformat_find_stream_info 发现媒体流
→ 选择第一条音频流和第一条视频流并打开解码器
→ 创建 audioq / videoq
→ 启动 SDL 音频设备和视频在线程，或为纯视频启动 SDL 定时器
→ 读线程循环 av_read_frame
→ 按 stream_index 把 Packet 放入对应队列
→ 音频回调取包、解码、swr_convert 为 S16 PCM、填入 SDL stream
→ 视频在线程取包、解码、根据 audio_clock 同步、sws_scale 为 RGB32
→ QImage::copy 后跨线程发送给 GUI
→ MyOpenGLWidget::paintGL 上传纹理并显示
→ EOF 后等待队列排空
→ 停止消费者，依次释放队列、解码器和 AVFormatContext
```

### 3. 三个核心技术点

1. `VideoPlayer::run` 是 Packet 生产者，SDL 音频回调、SDL 视频在线程或纯视频定时器是消费者；`PacketQueue` 用互斥锁和 FFmpeg 引用计数保存压缩数据。
2. 音频使用 `avcodec_decode_audio4 + swr_convert` 输出设备需要的 S16 PCM；视频使用 `avcodec_decode_video2 + sws_scale` 输出 RGB32，再通过 `QImage::copy` 跨线程交给 GUI/OpenGL。
3. 项目把 PTS 按各流 `time_base` 统一换算成微秒；有音频时使用音频主时钟，纯视频按帧率定时；seek 使用关键帧跳转、队列 flush 和解码器 flush。

### 4. 采用当前方案的三个原因

1. **采用方案：读线程负责解封装，音频和视频消费者通过两个 PacketQueue 独立取包。**采用原因：文件读取、音频设备和视频渲染的节奏不同，队列能解耦生产与消费；水位限制还能避免读线程把整个媒体文件快速读入内存。
2. **采用方案：存在音频时使用 audio_clock 作为主时钟，视频领先时等待；纯视频使用 SDL 定时器驱动。**采用原因：声卡按固定采样率持续消耗 PCM，随意停顿或丢弃音频容易产生断音；调节视频通常更自然，而纯视频没有音频时钟，必须用帧率控制播放速度。
3. **采用方案：GUI 线程只提交 seek 请求，读线程执行向前关键帧跳转，并同时清理 PacketQueue 和解码器缓存。**采用原因：`av_read_frame` 与 `av_seek_frame` 操作同一个 `AVFormatContext`，放在读线程可避免并发访问；H.264 等帧间编码通常需要从关键帧开始，只清队列又无法删除解码器内部旧参考帧。

### 5. 两个替代方案及比较

1. 使用 `SDL_QueueAudio` 主动推送 PCM：控制流程更直观，也不在实时回调中执行解码和重采样；当前 callback 拉取方案能自然跟随声卡节奏，但回调内工作较重，缺包只能补静音。
2. 解码后保留 YUV，在 OpenGL shader 中完成 YUV→RGB：可以减少 CPU `sws_scale`、RGB 缓冲复制和传输带宽；当前 RGB32→QImage→纹理方案与 Qt 集成简单，但每帧转换、复制和重新上传纹理的开销较大。

### 6. 三个异常场景

1. `audioq` 暂时为空：`audio_callback` 保留或填充静音，避免声卡读取未初始化数据；`videoq` 暂时为空时视频在线程短暂延迟后重试。
2. seek 失败：当前只记录错误，之前设置的等待 FLUSH 标志没有完整恢复，消费者可能等待一个不会到达的 FLUSH，存在卡住或持续静音风险。
3. EOF 或用户 stop：EOF 不能立即释放，因为队列和解码器中仍可能有待播放数据；stop 设置 `quit` 并关闭消费者，但 `wait(3000)` 的结果未检查，超时后仍可能存在旧线程访问对象的风险。

### 7. 当前实现的不足

- 使用已过时的 `avcodec_decode_audio4`、`avcodec_decode_video2` 和 `AVStream::codec`，未迁移到 `avcodec_send_packet/receive_frame`。
- 同步算法只有“视频领先则轮询等待”，视频严重落后时不主动丢帧，也没有动态同步阈值。
- `audio_clock` 在解码/填充缓冲时推进，并非精确的声卡实际播放位置；一个 Packet 包含多帧音频时，重复使用 Packet PTS 也可能使时钟推进不严谨。
- `quit`、`isPause`、`readFinished`、seek 标志及两个时钟被多个线程直接读写，没有原子变量或统一锁；部分队列字段也被绕过队列锁直接读取。
- 音频每帧重新创建 `SwrContext`；视频每帧执行 `sws_scale`、`QImage::copy` 和 `glTexImage2D`，CPU 与内存复制开销较大。
- EOF 连续失败约 3 秒才标记 `readFinished`，且未严格区分 EOF、临时网络错误和 `EAGAIN`，也没有显式排空解码器延迟帧。
- `setFileName()` 已经调用 `start()`，`PlayerDialog` 又重复调用一次；`stop(true)` 忽略 `wait(3000)` 的超时结果。
- FLUSH 使用内容为 `"FLUSH"` 的特殊 Packet 判断，缺少更可靠的队列节点类型或 serial 机制。

### 8. 30 秒回答

项目播放器由一个 `VideoPlayer` 读线程、两个线程安全 Packet 队列、SDL 音频回调和 SDL 视频在线程组成。读线程通过 FFmpeg 打开媒体、发现流、解封装并分发 Packet；音频侧解码和重采样成 S16 PCM 交给 SDL，视频侧解码并转换成 RGB32，通过 Qt 信号交给 OpenGL 控件显示。有音频时采用音频主时钟，视频领先就等待；seek 在读线程向前跳到关键帧，并同时清空队列和解码器缓存。EOF 后等待队列排空再按消费者优先的顺序释放资源。

### 9. 2 分钟回答

播放入口是 `PlayerDialog::playLocalFile` 或打开 URL 的槽，调用 `VideoPlayer::setFileName` 启动 QThread。`VideoPlayer::run` 使用 `avformat_open_input` 和 `avformat_find_stream_info` 打开输入并发现流，当前选择第一条音频流和第一条视频流，打开对应解码器并创建 `audioq`、`videoq`。之后读线程循环 `av_read_frame`，根据 `stream_index` 把压缩 Packet 放入对应队列；队列通过 `av_packet_ref` 持有底层缓冲区的独立引用，读线程可以释放自己的引用。

音频由 SDL callback 按声卡节奏拉取数据，`audio_decode_frame` 从 `audioq` 取包、解码成 Frame，再用 `swr_convert` 统一成设备要求的 S16 PCM。视频有音频时由独立 SDL 线程解码，纯视频则用 SDL 定时器按帧率驱动；解码后的像素用 `sws_scale` 转成 RGB32，`QImage::copy` 让图像脱离会复用的 RGB 缓冲区，再通过 Qt 跨线程信号交给 GUI 中的 `MyOpenGLWidget`。

时间戳按各自 `time_base` 换算成微秒。有音频时以 `audio_clock` 为主，视频 PTS 领先则短暂等待。seek 由 GUI 写请求、读线程执行 `av_seek_frame`，先向前找到关键帧，再清空未解码 Packet，通过 FLUSH Packet让消费者调用 `avcodec_flush_buffers`，最后丢弃目标时间以前的帧。EOF 后不能立刻释放，要等两个队列排空并停止音视频消费者。当前不足是同步策略简单、没有落后丢帧、时钟不够精确、跨线程状态同步不足，并且仍使用旧版 FFmpeg 解码 API和较多 CPU 转换复制。

### 10. 五个常见追问及参考答案

1. **问：AVPacket 和 AVFrame 有什么区别，为什么中间还需要队列？**  
   **答：**AVPacket 通常保存解封装后、解码前的压缩数据，例如 H.264 或 AAC；AVFrame 保存解码后的原始图像或 PCM 样本。读文件、声卡消费和视频显示的速度不同，两个 PacketQueue 将一个解封装生产者与音视频消费者解耦，并通过水位控制限制内存增长。`packet_queue_put` 使用 `av_packet_ref` 增加底层缓冲区引用，消费者取出后负责 `av_packet_unref`。

2. **问：为什么使用音频作为主时钟，当前实现准确吗？**  
   **答：**声卡以固定采样率持续消费 PCM，频繁暂停或丢弃音频容易产生断音，因此常见做法是保持音频连续，让视频调整显示节奏。当前项目的视频领先时等待音频，但 `audio_clock` 在解码并填充 SDL 缓冲时推进，不是扣除设备缓存后的真实播放位置，而且没有处理视频严重落后的丢帧，所以它只是一种基础同步方案。

3. **问：seek 为什么既要 `packet_queue_flush`，又要 `avcodec_flush_buffers`？**  
   **答：**`packet_queue_flush` 清除尚未进入解码器的旧位置 Packet；`avcodec_flush_buffers` 清除已经进入解码器的参考帧和内部缓存。只清队列仍可能输出旧声音或旧画面，只清解码器又会让队列里的旧 Packet 重新进入解码器。项目通过特殊 FLUSH Packet让清理解码器的动作在各自消费线程执行。

4. **问：读到 EOF 后为什么不能立即关闭解码器和销毁队列？**  
   **答：**`av_read_frame` 没有新 Packet，只说明生产结束，队列里可能还有未播放 Packet，解码器内部也可能持有数据。音频回调和视频在线程仍会访问队列、解码器和 `VideoState`；提前释放会造成尾部被截断或悬空访问。当前流程先设置 `readFinished`，等消费者排空并退出，再关闭音频设备、等待视频在线程、销毁队列和解码器。

5. **问：如果把播放器改成更接近生产级，你会优先优化什么？**  
   **答：**首先将跨线程标志和时钟改为明确的原子变量、锁或消息驱动状态机，并检查所有线程等待结果，保证生命周期安全；其次迁移到 `avcodec_send_packet/receive_frame`，建立包含设备延迟校正、动态阈值和落后丢帧的主时钟同步；最后复用 `SwrContext`，让视频保留 YUV 并在 OpenGL shader 中转换，配合有界 GUI 帧队列或只保留最新帧，减少转换、复制和信号积压。

## 面试知识卡 03：音视频录制器

### 1. 一句话说明模块作用

录制器采集桌面、摄像头和麦克风，把原始图像与 PCM 转换为编码器需要的 YUV420P 和 FLTP，通过独立编码线程生成 H.264/AAC，并按时间戳交错封装为 FLV 文件。

### 2. 一条完整业务流程

```text
用户点击开始录制
→ 设置输出路径、屏幕分辨率、25FPS和码率
→ 初始化FLV输出、H.264和AAC编码器并写文件头
→ OpenCV采集摄像头，显示置顶摄像头预览窗
→ GUI线程抓取整个桌面，间接把预览窗录入桌面
→ RGB24转换为YUV420P，记录采集相对时间并进入视频队列
→ QAudioInput采集44.1kHz双声道16bit PCM
→ 按1024采样点整理并把S16 packed转换为FLTP planar
→ 进入音频队列
→ 编码线程比较两路下一帧的真实时间，选择更早的一路
→ 原始Frame编码为H.264/AAC Packet
→ Packet时间戳转换后交错写入FLV
→ 停止采集并消费剩余原始队列
→ 写trailer、关闭编码器和文件
```

### 3. 三个核心技术点

1. 三种采集源先统一为编码器输入格式：视频 RGB/BGR 转 YUV420P，音频 S16 packed 转 FLTP planar，并按 AAC 的 1024 个采样点组织帧。
2. 音视频原始帧使用两个互斥队列与编码线程解耦；视频按固定帧率和采集相对时间稳帧，音频按累计采样数生成 PTS。
3. 编码线程带着各自 time_base 比较下一帧时间，将 Frame 编码为 H.264/AAC Packet，完成时间戳转换后由 FFmpeg 交错写入 FLV。

### 4. 采用当前方案的三个原因

1. **采用方案：OpenCV采集摄像头、Qt抓取桌面、QAudioInput采集麦克风。**采用原因：这些库已与 Qt 客户端集成，能以较低实现成本取得三类原始数据，适合当前教学和桌面应用范围。
2. **采用方案：采集侧完成格式转换并通过双帧队列交给独立编码线程。**采用原因：采集节奏、编码耗时和磁盘写入可能抖动，队列能避免一次慢编码直接阻塞设备采集，并允许编码线程按音视频时间轴选择数据。
3. **采用方案：H.264 + AAC + FLV，并为视频使用 superfast、zerolatency 和较短 GOP。**采用原因：组合兼容性较好、顺序写入和流式传输友好，也便于未来复用到 RTMP；快速低延迟参数优先保证实时编码和较快关键帧恢复。

### 5. 两个替代方案及比较

1. 在内存中缩放并叠加摄像头帧，再使用 DXGI Desktop Duplication 或 Windows Graphics Capture 获取桌面：布局稳定、可后台运行且性能更好，但平台相关代码和 GPU/像素格式处理更复杂；当前置顶窗口后抓全桌面实现简单，却依赖窗口可见性和 GUI 响应。
2. 每次录制创建独立 RecordingSession，内部使用有界阻塞队列和 RAII Frame：状态、所有权和重复录制更清晰，能实现背压、取消和错误回滚；当前长期复用 QThread 对象和裸指针队列代码量较少，但生命周期和多次录制不可靠。

### 6. 三个异常场景

1. 摄像头打开失败：当前上层仍可能进入录制状态，音频又可能持续等待视频起点并被丢弃；合理做法是返回初始化失败并回滚其他资源。
2. 编码或磁盘长期慢于采集：当前无界队列可能持续增长，导致内存和延迟增加；应设置容量、视频过载丢旧原始帧、记录丢帧并向上层施加背压。
3. 用户停止或程序退出：当前会停采集、尝试清队列并写 trailer，但没有显式排空编码器，且线程等待超时未检查，可能丢尾部数据或发生对象销毁后的访问。

### 7. 当前实现的不足

- 画中画依赖置顶窗口进入桌面截图，受遮挡、窗口位置、桌面合成和 GUI 卡顿影响。
- 桌面截图和音频定时处理主要位于 GUI 线程，可能导致界面和采集互相影响。
- 原始帧队列无容量上限、没有条件变量，部分队列大小读取绕过锁并以短暂休眠轮询。
- 跨线程停止标志是普通 bool，摄像头关闭和编码退出存在数据竞争。
- 缓冲区以裸指针传递，存在 malloc/free、new/delete 和 av_malloc/av_free 配对不统一，源码中还有 malloc 后 delete[] 的未定义行为。
- 没有显式 flush H.264/AAC 编码器，文件尾部可能丢失延迟 Packet。
- wait 超时结果未检查，摄像头线程也没有完整 join；采集对象和重采样资源析构不完整。
- 第二次开始录制时停止标志、PTS、队列和编码上下文没有形成完整的新会话重置。
- 参数基本写死，音频声道数与布局的设置顺序、Qt 音频有符号格式与重采样输入格式存在一致性风险。

### 8. 30 秒回答

录制模块分为采集、转换、队列、编码和封装五层。摄像头由 OpenCV 采集，桌面由 Qt 截图，视频转为 YUV420P；麦克风由 QAudioInput 采集 PCM，再转为 AAC 需要的 FLTP。音视频通过两个队列交给编码线程，视频 PTS 按帧序号、音频 PTS 按累计采样数推进，编码线程选择时间更早的一路，生成 H.264/AAC Packet 并交错写入 FLV。当前实现完成了主链，但队列无界、跨线程状态和缓冲区所有权不够严格，停止时也没有显式排空编码器。

### 9. 2 分钟回答

用户开始录制后，客户端以屏幕分辨率、25FPS和固定码率初始化 FLV、H.264和AAC编码器。视频侧用 OpenCV读取摄像头并显示置顶预览窗，再由 GUI线程抓取整个桌面，因此摄像头窗会作为桌面内容进入输出；桌面 RGB24 转换为 YUV420P，记录采集相对时间后进入视频队列。音频侧使用 QAudioInput读取44.1kHz双声道16bit PCM，缓存到1024个采样点后转换成FLTP并进入音频队列。

编码线程根据两路 next PTS 和各自 time_base 选择真实时间更靠前的一路。视频按25FPS让帧序号递增，采集抖动时淘汰过旧原始帧或复用上一画面；音频按累计采样点生成PTS，避免定时器抖动直接影响时间轴。Frame送入H.264/AAC编码器后取出Packet，把编码器时间戳转换到输出流时间基，再由FFmpeg交错写入FLV。选择FLV是因为H.264/AAC兼容性和顺序写入、RTMP复用能力较好，superfast和zerolatency优先实时性但牺牲压缩效率。

停止时应先停生产者、排空原始队列，再排空两个编码器内部的延迟Packet，写trailer、关闭文件并等待线程退出。当前项目缺少编码器flush，队列无界、普通bool跨线程读写、裸指针所有权和重复录制状态重置也不够完善，因此属于核心流程完整但仍需生产化治理的实现。

### 10. 五个常见追问及参考答案

1. **问：请介绍录制功能从设备采集到文件生成的完整流程。**  
   **答：**摄像头、桌面和麦克风先产生原始图像与PCM，视频转换为YUV420P，音频按1024采样点整理并转为FLTP，分别进入两个原始帧队列。编码线程按时间轴选择一路，把Frame编码成H.264/AAC Packet，转换时间戳后交错写入FLV；停止时再处理队列、编码器和容器收尾。

2. **问：为什么采集和编码之间要加队列，编码跟不上时怎么办？**  
   **答：**设备采集有固定节奏，而编码和磁盘写入耗时会抖动，队列可以避免一次慢编码直接阻塞下一次采集。当前无界队列会造成内存和延迟增长；生产化时应使用有界阻塞队列，视频过载时丢弃过旧原始帧或只保留最新帧，音频优先保持连续，并记录压力和丢帧指标。

3. **问：录制时怎样为音视频生成时间戳并保持交错？**  
   **答：**视频固定25FPS，PTS按帧序号递增，时间基是1/25；音频按累计采样数推进，每帧1024个采样点，时间基通常是1/44100。编码线程不能比较原始整数，而要带着各自time_base比较真实时间，选择更早的一路编码；Packet随后还要从编码器时间基转换到输出流时间基再写入封装器。

4. **问：用户点击停止后，怎样保证文件完整？**  
   **答：**先停止摄像头和麦克风，保证没有新Frame；再消费完两个原始帧队列；然后分别向H.264和AAC编码器发送结束信号，持续读取延迟Packet直到EOF；接着写容器trailer、关闭编码器和文件，最后确认所有线程退出。当前项目缺少编码器排空且忽略等待超时结果，这是明确不足。

5. **问：你的画中画怎样实现，生产环境会如何改进？**  
   **答：**当前先把摄像头显示成置顶小窗，再抓取整个桌面，小窗因此被录入，优点是实现简单；缺点是依赖窗口可见性、位置和桌面合成，也会录入无关通知。生产环境会分别获取桌面帧和摄像头帧，在内存或GPU中缩放叠加，并使用更高效的平台桌面采集API。

## 面试知识卡 04：客户端网络与自定义协议

### 1. 一句话说明模块作用

客户端网络模块在 Qt 页面与 TCP socket 之间提供统一协议门面，用长度帧恢复 TCP 消息边界，在独立接收线程中收取响应，再通过 Qt 信号把媒体列表、上传和下载结果交回界面。

### 2. 一条完整业务流程

```text
页面发起业务请求
→ 协议门面组装 Ping、列表、上传或下载请求体
→ 传输层添加“4字节包体长度”
→ 循环 send，直到完整帧发送完毕
→ 服务端处理并返回长度帧
→ 客户端接收线程先读满长度，再读满包体
→ 校验消息类型、固定字段和动态载荷长度
→ Qt 排队信号把业务结果交给 GUI 页面
→ 页面更新列表或根据确认 offset 发送/请求下一个 64KiB 块
→ 传输结束后更新本地任务状态
```

### 3. 三个核心技术点

1. TCP 是无消息边界的可靠有序字节流；客户端用 4 字节长度头和 `sendAll/recvAll` 循环处理半包与多次收发，而不是假设一次 send 对应一次 recv。
2. `TcpClient` 只负责连接、长度帧和完整收发，`AVNetworkClient` 负责请求结构、消息类型、字段校验和 Qt 业务信号，页面不直接依赖 Winsock。
3. 上传和下载采用停止等待式 64 KiB 分块：收到上一块的服务端确认偏移后才继续，便于顺序控制和断点恢复，但吞吐会受 RTT 限制。

### 4. 采用当前方案的三个原因

1. **采用方案：4 字节包体长度＋二进制包体。**采用原因：TCP 没有应用消息边界，长度头可以用较小实现成本准确识别完整包体，也能在分配内存前校验上限。
2. **采用方案：传输层 `TcpClient` 与协议门面 `AVNetworkClient` 分层。**采用原因：页面无需处理 socket 和粘包半包，协议字段变化主要集中在协议层，连接错误、帧错误和业务错误也更容易分开定位。
3. **采用方案：独立阻塞接收线程＋Qt 信号通知，并对文件块使用停止等待。**采用原因：阻塞式读满逻辑直观，接收不会直接卡住 GUI；逐块确认让 offset 和恢复状态容易推理，符合当前项目规模和教学目标。

### 5. 两个替代方案及比较

1. 使用 `QTcpSocket` 并把 socket 放入专用 `QThread`，依靠事件循环和 receive buffer 增量拆包：更贴合 Qt、可统一异步连接和发送，但要明确对象线程亲和性、线程启动顺序和退出流程。
2. 使用 Protobuf/FlatBuffers 等序列化协议并增加统一协议头、版本、请求 ID 和网络字节序：兼容性和演进能力更好，但引入代码生成、依赖和更高学习成本；当前 packed struct 紧凑直接，却强依赖两端结构布局和字节序一致。

### 6. 三个异常场景

1. 长度头合法但对端迟迟不发送完整包体：当前专用接收线程可能长期阻塞；应设置接收超时、空闲连接超时或取消机制。
2. 动态载荷声明长度与实际帧长度不一致：外层帧已经完整，但继续按错误内层长度解析可能越界，因此当前应拒绝该业务包并记录协议错误。
3. 用户主动断开而接收线程正阻塞：仅修改运行标志不能唤醒 `recv`；当前通过 shutdown/close socket 使 `recv` 返回，再 join 接收线程。

### 7. 当前实现的不足

- 长度、整数字段和 packed struct 直接使用主机字节序及本机布局，没有统一协议头、版本、请求 ID、校验和和兼容升级机制。
- 客户端最大接收包为 1 MiB，服务端最大包体为 256 KiB，限制没有统一为共享协议常量。
- 已实现 MySQL 身份认证和 ownerUserId 基础控制；仍没有 TLS、长期 session、角色和私有媒体权限。
- 接收线程没有明确的包体读取超时、自动重连和心跳失效处置。
- 连接等待、同步发送、上传文件读取和下载文件写入仍可能发生在 GUI 线程，界面可能卡顿。
- 缺少统一发送队列；发送锁只能保证并发帧不交错，不能让网络和文件 I/O 异步化。
- 停止等待式分块只允许一个块在途，简单但高 RTT 环境吞吐较低。
- 部分畸形响应和业务错误只记录日志，错误传播和页面状态回滚不够统一。

### 8. 30 秒回答

客户端网络分为传输层和协议层。传输层维护 TCP 连接，使用“4 字节长度＋包体”以及循环收发解决半包和消息边界；协议层组装媒体列表、上传下载等请求，并把响应解析成 Qt 业务信号。接收由独立线程完成，上传下载每次传一个 64 KiB 块并等待服务端确认 offset。当前方案简单易验证，但协议缺少版本和网络字节序，发送与文件 I/O 也没有完全移出 GUI 线程。

### 9. 2 分钟回答

这个模块首先把 socket 传输和业务协议拆开。`TcpClient` 只关心连接以及完整帧收发：发送时在包体前加 4 字节长度并循环 send；接收线程先读满长度，校验上限，再读满包体，所以即使 TCP 出现半包或连续到达多个包也能恢复边界。`AVNetworkClient` 再根据消息类型解析 Ping、媒体列表、上传初始化/恢复/分块/完成和下载初始化/分块/完成，动态载荷还要核对内部数据长度与实际包体长度。

接收线程不直接改界面，而是发出 Qt 信号，由属于 GUI 线程的协议对象和页面处理。上传下载采用停止等待：每个块最多 64 KiB，上一块得到确认 offset 后才继续，顺序和恢复逻辑比较清楚，但网络 RTT 高时吞吐有限。断开时必须先 shutdown/close socket 唤醒阻塞 recv，再 join 接收线程。

它的生产化不足主要有三类：协议直接传 packed struct 和主机字节序，缺少版本、请求 ID、认证和 TLS；接收缺少超时和自动重连；连接、同步发送和本地文件 I/O 仍可能卡住 GUI。改进时会让专用网络线程独占 socket 和发送队列，把文件读写交给任务线程，并完善协议元数据、错误传播和流量控制。

### 10. 五个常见追问及参考答案

1. **问：TCP 已经可靠，为什么应用层还要自己定义消息边界？**  
   **答：**TCP 可靠、有序地传输字节，但不保留每次 send 的边界。一个业务包可能被多次 recv 才收全，多个业务包也可能在一次 recv 中连续到达，因此应用层仍要用长度头或分隔符恢复消息。本项目使用 4 字节长度头，并循环读满对应包体。

2. **问：为什么要把底层连接和业务协议分成两层？**  
   **答：**底层连接解决 socket 生命周期和完整帧收发，协议层解决消息类型、字段含义、动态载荷和业务通知。这样页面不依赖 Winsock，协议调整不必改动连接算法，出错时也能区分连接失败、帧不完整、字段非法和业务拒绝。

3. **问：接收线程怎样安全地更新 Qt 界面？**  
   **答：**接收线程只产生完整 `QByteArray` 并发信号，不直接访问控件。接收对象属于 GUI 线程时，跨线程 AutoConnection 会采用排队调用，把槽执行投递到 GUI 事件循环。当前源码锚点是 `TcpClient::recvLoop`、`AVNetworkClient::onPacketReceived` 和各页面业务槽。

4. **问：客户端断开时，为什么不能只把运行标志设为 false？**  
   **答：**线程可能正阻塞在 `recv`，没有机会重新检查标志。必须 shutdown/close socket 让阻塞调用返回，接收循环才能退出，随后再 join，避免对象析构后后台线程继续访问成员。

5. **问：为什么上传下载每次只让一个块在途，如何提高吞吐？**  
   **答：**单块确认使服务端确认 offset、顺序写入、错误恢复和任务持久化都更简单，适合当前实现；代价是每 64 KiB 都等待一次 RTT。可增加窗口化流水线和块序号，允许多个块在途，同时维护累计确认、乱序重排、重传和发送队列上限，但状态机复杂度明显增加。

## 面试知识卡 05：epoll LT Reactor

### 1. 一句话说明模块作用

服务端使用 epoll LT 单线程 Reactor 统一管理监听、连接、非阻塞收发和协议帧状态，把耗时文件业务交给线程池，并通过连接唯一身份过滤断线后的陈旧结果。

### 2. 一条完整业务流程

```text
服务端创建非阻塞listen socket并注册epoll
→ epoll_wait返回监听事件
→ 循环accept到EAGAIN
→ 创建ConnectionContext（单连接状态对象）并分配connectionId
→ 注册EPOLLIN和EPOLLRDHUP
→ 可读时循环recv到EAGAIN
→ 字节追加到receiveBuffer（接收缓冲区）
→ 按“4字节长度＋包体”循环提取完整帧
→ 轻量请求由Reactor处理，文件业务提交worker
→ 响应加入sendQueue（待发送队列）并立即尝试发送
→ EAGAIN时开启EPOLLOUT，从offset继续发送
→ 队列清空后关闭EPOLLOUT
→ 断线时从epoll和连接表删除并关闭socket
```

### 3. 三个核心技术点

1. LT 模式只要数据仍可读就会重复通知，但 socket 仍设置为非阻塞；读取循环在 `EAGAIN（当前暂时无数据）` 时把控制权还给 Reactor，避免一条连接卡住全部客户端。
2. 每条连接用 `ConnectionContext（单连接状态对象）` 保存 `receiveBuffer（接收缓冲区）`、`sendQueue（待发送队列）`、部分发送 offset 和在途任务状态，能够跨多次事件保存协议进度。
3. worker 不持有连接对象也不直接发送，只返回带 `connectionId（连接唯一身份）` 的结果；Reactor 校验身份后再投递，避免 fd 复用导致旧响应误投。

### 4. 采用当前方案的三个原因

1. **采用方案：epoll LT＋全部网络 socket 非阻塞。**采用原因：一个主线程可以管理多条大部分时间空闲的连接；LT 容错和理解成本低于 ET，非阻塞保证任何客户端都不能把事件循环卡住。
2. **采用方案：每连接独立收发缓存＋按需监听 EPOLLOUT。**采用原因：TCP 会半包、粘包和部分发送，连接对象必须保存跨事件进度；socket 通常可写，只有 `send（向内核发送缓冲区提交字节）` 返回 EAGAIN 时才监听写事件，可以避免空队列造成 CPU 无意义唤醒。
3. **采用方案：Reactor 独占连接状态，worker 只返回完成结果，并使用 connectionId 校验。**采用原因：能够统一发送顺序、部分发送进度和关闭权，同时避免悬空指针、并发 send 以及 fd 复用误投。

### 5. 两个替代方案及比较

1. epoll ET：就绪变化时通常只通知一次，事件次数可能更少，但 accept、recv、send 都必须严格循环到 EAGAIN，遗漏一次读取可能导致连接长期得不到处理；当前 LT 更适合先保证正确性。
2. 多 Reactor 或主从 Reactor：多个 I/O 线程分别管理连接，可突破单 Reactor CPU 瓶颈并利用多核，但需要连接分配、跨线程投递、负载均衡和更严格的状态所有权；当前单 Reactor 结构更简单。

### 6. 三个异常场景

1. 客户端只发送长度头或持续慢速发送：不完整数据保留在 receiveBuffer；若累计超过每连接 4 MiB 上限则关闭，避免无限占用内存。
2. 客户端长期不读取响应：`send` 可能部分完成或返回 EAGAIN，数据保存在 sendQueue；累计超过 4 MiB 上限则关闭慢连接。
3. worker 执行期间客户端断开并发生 fd 复用：完成结果回到 Reactor 后发现 connectionId 不存在或不匹配，直接丢弃，不向新连接发送旧响应。

### 7. 当前实现的不足

- 单 Reactor 的拆包、轻量协议和所有收发都在一个线程，连接数或网络处理量继续上升时可能成为单核瓶颈。
- `receiveBuffer` 使用 vector 头部 erase，频繁拆包可能发生内存移动；可改为读写下标、环形缓冲区或分段缓冲。
- 连接表使用 `std::map`，查找为 O(log n)；大量连接时可评估哈希表，但当前规模下差异有限。
- 每连接只允许一个文件业务任务在途，保证顺序但限制同一连接的并行吞吐。
- 只有缓存容量限制，没有完整的连接级速率限制、写超时、空闲连接清理和公平调度；持续活跃连接的读循环也可能影响其他连接延迟。
- `closing` 字段当前没有形成明确关闭状态机，错误原因和优雅关闭流程较简单。
- 单调递增 connectionId 理论上存在极长期溢出边界，当前项目规模下不构成现实问题。

### 8. 30 秒回答

服务端采用 epoll LT 单线程 Reactor。监听和客户端 socket 都是非阻塞的，Reactor负责 accept、循环recv、长度帧拆包、发送队列和连接关闭。TCP部分发送时用data加offset保存进度，只在发送缓冲区满时开启EPOLLOUT，队列清空后关闭。耗时文件业务交给worker，但worker不直接操作连接；结果回来后用connectionId校验，防止客户端断开和fd复用造成旧响应误投。

### 9. 2 分钟回答

服务端从 `main` 进入 `EpollServer` 后，创建非阻塞监听socket和epoll。监听fd可读时循环accept到EAGAIN，为每条连接建立ConnectionContext，保存接收缓冲、发送队列、活动时间、connectionId和是否存在在途业务任务。客户端可读时，Reactor循环recv到EAGAIN，把字节追加到receiveBuffer，再根据4字节长度头增量拆包：不完整尾部保留，完整帧提取后继续解析剩余数据。

响应发送也不能假设一次send完成。每个PendingSend保存完整帧和offset，send返回部分长度就推进offset；返回EAGAIN说明内核发送缓冲区暂时满，此时才开启EPOLLOUT，后续可写时继续发送，队列清空立即取消监听。接收和发送队列都设置4MiB上限，防止慢客户端无限占用内存。

Reactor独占socket、ConnectionContext、收发队列、epoll状态和关闭权。文件业务提交线程池时只复制请求、fd和connectionId，worker生成结果后再唤醒Reactor。Reactor重新检查connectionId和当前fd映射，因此即使旧连接关闭后相同fd被新客户端复用，也不会把旧响应发给新连接。当前不足是单Reactor、vector头部erase、单连接一个在途任务以及缺少完善的限速和超时策略。

### 10. 五个常见追问及参考答案

1. **问：LT模式会重复通知，为什么socket仍必须设置为非阻塞？**  
   **答：**EPOLLIN只表示当前至少有数据可读，不保证读取循环中的下一次recv仍有数据。如果socket阻塞，读完现有数据后的下一次recv可能卡住整个Reactor；非阻塞模式会返回EAGAIN，让主线程继续处理其他连接。

2. **问：服务端如何同时处理TCP半包和粘包？**  
   **答：**每次recv的字节先追加到receiveBuffer。少于长度头或不足完整帧就保留；凑齐后提取并删除一帧，再继续循环检查剩余字节，能继续组成帧就继续处理，最后的不完整尾部留到下次EPOLLIN。

3. **问：为什么不能永久监听EPOLLOUT，部分发送怎样恢复？**  
   **答：**socket大多数时间可写，永久监听会让epoll在无数据可发时反复唤醒。项目为待发送帧保存data和offset，先主动send；EAGAIN时保留进度并开启EPOLLOUT，重新可写后从offset继续，队列清空后立即取消写事件。

4. **问：fd已经能标识socket，为什么还要connectionId？**  
   **答：**fd是可复用的整数。旧连接断开后，新连接可能获得相同fd，而旧worker任务随后才完成。每次连接分配不同connectionId，完成时同时核对连接身份，可以识别并丢弃旧任务结果。

5. **问：为什么worker不能保存ConnectionContext指针并直接send？**  
   **答：**`ConnectionContext*（连接状态对象的指针）`可能在客户端断开后悬空；多个worker并发send还会破坏响应顺序、发送队列和部分发送offset；fd也可能已经复用。让Reactor独占连接，worker只返回结果，可以把生命周期和I/O状态收敛到一个线程。

## 面试知识卡 06：动态线程池与跨线程协作

### 1. 一句话说明模块作用

服务端用4到8个worker组成有界动态线程池执行目录和文件业务，再通过completion queue保存结果、eventfd唤醒Reactor，由Reactor统一校验连接并发送响应。

### 2. 一条完整业务流程

```text
Reactor识别媒体列表或上传下载请求
→ 设置businessTaskInFlight（该连接已有业务任务）
→ 请求包副本进入最多256任务的FIFO队列
→ 空闲worker不足时按需扩容，最多8个
→ worker执行MySQL、Argon2id或文件读写
→ 生成CompletedTask（业务完成结果）
→ 加锁放入completion queue（跨线程完成队列）
→ write eventfd唤醒epoll_wait
→ Reactor批量swap取走结果
→ 用connectionId确认连接仍有效
→ 响应进入sendQueue并非阻塞发送
→ 清除在途标志，继续解析该连接缓存请求
```

### 3. 三个核心技术点

1. 线程池常驻4个核心线程，等待任务多于空闲线程时按需增加非核心线程，最多8个；非核心线程空闲60秒后退出，随后由线程池join回收。
2. `m_tasks（待执行任务队列）`最多256个，满载时submit返回false，Reactor回复server busy，用显式背压代替无限内存积压。
3. `m_completionQueue（跨线程完成队列）`保存详细结果，`eventfd（可被epoll监听的内核计数器fd）`只负责唤醒；worker不持有连接对象，Reactor凭connectionId过滤断线或fd复用后的旧结果。

### 4. 采用当前方案的三个原因

1. **采用方案：4核心、8最大、非核心空闲60秒退出的动态线程池。**采用原因：正常负载下复用常驻线程，突发文件业务时临时提高并发，高峰结束后又能释放多余线程资源。
2. **采用方案：256容量FIFO有界队列＋队列满返回server busy。**采用原因：限制内存和排队延迟，在处理能力耗尽时形成明确背压，避免表面不拒绝、实际最终拖垮服务端。
3. **采用方案：互斥完成队列＋eventfd通知＋Reactor统一投递。**采用原因：队列适合传递复杂响应，eventfd能直接纳入epoll；统一由Reactor操作连接可以保持发送顺序和生命周期安全。

### 5. 两个替代方案及比较

1. 每任务创建线程或使用detach：实现表面直接，但线程数量、栈内存、创建开销和服务器停止生命周期不可控；线程池可复用并限制并发。
2. 固定线程池＋pipe/socketpair通知：固定池策略更简单但不能适应突发负载；pipe或socketpair也能唤醒epoll且可传少量数据，但eventfd作为计数通知更轻量，复杂结果仍应放独立队列。

### 6. 三个异常场景

1. 任务队列已满：submit返回false，清除该连接在途标志并构造server busy响应，而不是继续无限排队。
2. worker业务抛出异常：任务包装层记录error和closeConnection，仍把完成结果送回Reactor；线程池外层也捕获异常，避免一个任务终止整个worker线程。
3. worker期间客户端断开：Reactor按旧connectionId查不到连接，或当前fd对应对象的connectionId不匹配，完成结果被丢弃。

### 7. 当前实现的不足

- 扩缩容只看瞬时队列与空闲线程，没有使用CPU、磁盘负载、任务耗时和排队延迟等指标。
- 所有业务共用一个FIFO队列，没有任务优先级、每客户端公平性、取消、期限和执行超时。
- 一个阻塞不返回的文件任务可能让stop中的join长期等待。
- finished非核心线程主要等下次submit或最终stop才回收，没有独立管理线程持续回收。
- completion queue没有容量上限，Reactor处理不及时可能积压响应数据。
- 所有worker共用一把完成队列锁，规模扩大后可能竞争；Reactor一次处理全部完成结果也缺少批次公平控制。
- 请求包和std::function存在按值复制开销，线程参数固定为4/8/256/60秒，不能按机器配置调整。
- 线程池只保护自身队列和计数，UploadManager等共享业务对象仍必须自行保证线程安全。

### 8. 30秒回答

服务端把MySQL、Argon2id和文件读写从Reactor移到有界动态线程池。线程池常驻4个线程、最多扩到8个，任务队列最多256个，队列满返回server busy；非核心线程空闲60秒退出并统一join。worker完成后把带connectionId的结果放入completion queue，再写eventfd唤醒epoll。Reactor批量取出结果并重新校验连接，防止断线和fd复用导致旧响应或认证状态误投。

### 9. 2分钟回答

Reactor识别到媒体列表或上传下载请求后，不直接做磁盘I/O，而是复制请求和连接身份提交ThreadPool。线程池启动4个核心worker；当等待任务多于空闲worker且当前线程少于8时，每次提交可增加一个非核心worker。任务FIFO队列上限为256，满载直接拒绝并由服务端返回server busy。worker无任务时通过condition_variable休眠，非核心线程空闲60秒后标记finished退出，随后由reap或stop在锁外join。

worker只执行协议文件业务并生成CompletedTask，其中包含connectionId、协议类型、响应集合和错误信息。结果先进入互斥锁保护的completion queue，再向eventfd写1。eventfd已经注册到epoll，所以Reactor会从epoll_wait醒来，读取通知并通过swap快速取走一批完成结果。它先按connectionId反查当前fd，再找到ConnectionContext并再次比较身份；旧连接关闭或fd已复用就丢弃，否则清除businessTaskInFlight、把响应放入发送队列，并继续处理该连接缓存的请求。

该方案避免文件I/O阻塞所有连接，也避免worker并发操作socket和悬空连接对象。当前不足是扩缩容规则简单、FIFO没有公平性和超时、stop可能被永久I/O拖住、完成队列无界以及固定参数缺乏自适应。

### 10. 五个常见追问及参考答案

1. **问：为什么Reactor还需要线程池？**  
   **答：**Reactor负责所有连接的网络事件，如果直接执行MySQL、Argon2id和文件读写，一次慢业务就会拖延所有客户端。线程池把耗时业务移出I/O线程，同时通过最大线程数和固定数据库池限制并发。

2. **问：当前线程池怎样扩缩容，队列满了怎么办？**  
   **答：**启动4个核心线程；任务入队后，如果等待任务多于空闲线程且当前少于8个，就增加一个非核心线程。非核心线程空闲60秒后退出。队列最多256个，满时submit失败，服务端返回server busy。

3. **问：为什么要用条件变量，非核心线程退出后为什么仍需join？**  
   **答：**条件变量让无任务的worker休眠并处理虚假唤醒，避免短周期轮询耗CPU。线程函数返回只代表执行结束，joinable的std::thread对象仍必须join后才能安全销毁；detach会失去生命周期控制。

4. **问：为什么completion queue和eventfd缺一不可？**  
   **答：**完成队列保存connectionId、响应包和错误等真实数据；eventfd只负责把阻塞在epoll_wait的Reactor唤醒。只有队列Reactor不知道何时检查，只有eventfd又没有具体结果可处理。

5. **问：worker为什么不能直接send，旧任务结果怎样过滤？**  
   **答：**worker直接操作`ConnectionContext*（连接状态对象的指针）`可能发生悬空访问、并发破坏发送顺序和fd复用误投。它只返回结果；Reactor用旧connectionId反查fd，再比较当前连接对象的connectionId，不存在或不匹配就丢弃。

## 面试知识卡 07：上传、下载与断点续传

### 1. 一句话说明模块作用

项目通过64KiB分片、服务端确认offset、双方持久化任务记录和临时`.part`文件，实现上传和下载在断线以及客户端/服务端重启后的继续传输。

### 2. 一条完整业务流程

```text
上传：
初始化文件名/大小
→ 服务端生成transferId和resumeToken
→ 创建服务端.part与.task
→ 客户端按服务端confirmedOffset发送64KiB块
→ 服务端pwrite、fsync、持久化后返回receivedOffset
→ 全部确认后服务端把.part重命名到media目录

下载：
初始化取得远程size/mtime
→ 客户端创建本地.part与.download.json
→ 按本地offset请求64KiB块
→ 写入、flush并保存客户端offset
→ 中断时用JSON记录和.part实际大小的较小值恢复
→ 服务端确认远程文件未变化后继续读取
→ 完成后客户端把.part重命名为正式缓存文件
```

### 3. 三个核心技术点

1. 上传offset以服务端`receivedOffset（已可靠写入并持久化的偏移）`为权威；客户端send成功只表示字节进入本机TCP发送缓冲区。
2. 上传半成品位于服务端，因此持久化任务、凭证、大小和连接归属；下载半成品位于客户端，服务端可用文件名、offset和长度无会话读取。
3. 恢复前都使用保守偏移：上传服务端取总大小、任务记录和`.part`实际大小的最小值；下载客户端取JSON记录和本地`.part`实际大小的最小值。

### 4. 采用当前方案的三个原因

1. **采用方案：64KiB停止等待式分片，每块得到确认后再继续。**采用原因：顺序、重复块、跳跃块、错误恢复和内存上限容易推理，适合当前项目规模。
2. **采用方案：上传服务端`.part + .task + transferId/resumeToken`持久状态。**采用原因：上传半成品和可靠写入事实位于服务端，必须由服务端在断线和重启后恢复并防止其他连接接管。
3. **采用方案：下载客户端`.part + JSON`持久状态，服务端按offset无会话读取。**采用原因：服务端源文件已经是完整媒体，恢复进度只影响客户端本地半成品，无需为每个下载者长期保存会话。

### 5. 两个替代方案及比较

1. 滑动窗口或多块并行：多个块在途能降低RTT影响并提高吞吐，但需要块序号、累计确认、乱序重排、重传和更复杂的恢复状态；当前停止等待更简单。
2. 内容寻址或版本化分块：为文件和块保存版本ID、SHA-256和块清单，可发现内容变化、损坏和重复上传，并支持去重；代价是计算、存储、协议和元数据管理复杂度更高。

### 6. 三个异常场景

1. 上传.task记录与服务端.part大小不一致：取`min(expectedSize, recordedSize, actualSize)`，必要时截断多余数据并降低记录，宁可重传也不跳过未确认内容。
2. 下载JSON偏移与本地.part大小不一致：取两者较小值，截断未记录尾部或降低记录，再请求服务端确认恢复元数据。
3. 远程下载文件size或mtime变化：恢复初始化返回remote file changed，禁止向旧.part继续追加；当前活跃下载过程中的同大小替换仍可能漏检。

### 7. 当前实现的不足

- 上传和下载都没有整文件或分块强哈希，主要依赖大小、offset和mtime，不能证明内容完全一致。
- 下载块没有绑定初始化时的稳定文件版本，活跃下载时同大小替换可能形成新旧内容混合文件；完成协议只比较远程大小。
- 上传停止等待、每块fsync/任务持久化及UploadManager粗粒度全局锁限制吞吐和多客户端并发。
- 客户端上传读取、下载写入/flush和JSON保存位于GUI线程，可能造成界面卡顿。
- resumeToken已与ownerUserId联合校验，但没有TLS时仍是明文传输凭据。
- 客户端放弃上传不会立即删除服务端任务；孤立.part只记录日志，可能残留磁盘。
- 客户端JSON以double保存64位整数，极大文件存在精度边界，version字段写入但未验证。
- 下载完成前先删除同名旧缓存，随后rename失败会失去旧缓存。
- 没有磁盘空间预检查、传输配额、速率限制、任务取消协议和可配置TTL。

### 8. 30秒回答

项目上传和下载都使用64KiB停止等待式分片。上传半成品在服务端，所以服务端保存transferId、resumeToken、.part、任务元数据和确认offset，每块写入并持久化后才返回新偏移；下载半成品在客户端，因此客户端保存.part和JSON，服务端只按文件名、offset和长度无会话读取。恢复时双方都取记录与实际文件的安全较小值，下载还比较远程size和mtime。当前不足是RTT和fsync开销、粗粒度锁、GUI文件I/O以及缺少稳定版本和强哈希。

### 9. 2分钟回答

上传分初始化、分块和完成三阶段。初始化时服务端校验文件元数据，生成transferId和随机resumeToken，创建temp下的.part以及持久化.task。客户端每次从confirmedOffset读取最多64KiB，服务端只有在pwrite、fsync、stat和任务记录持久化全部成功后才返回receivedOffset，因此发送成功不能当成上传成功。重复的已确认块可以幂等返回，跳跃或部分重叠块返回offset mismatch。全部字节确认后，服务端核对记录与实际大小，再把.part重命名到media目录。

上传中断后客户端保留本地JSON，服务端解除连接绑定。恢复时客户端校验本地源文件路径、大小和mtime，再携带任务编号、token和元数据；服务端加载任务，取expectedSize、记录receivedSize和.part实际大小三者最小值作为安全offset，修正状态后重新绑定连接。因此客户端、服务端或双方重启，只要双方状态合法、本地源文件没变且任务未过期，都能恢复。

下载服务端不保存任务，因为正式媒体文件已经存在，每个请求带文件名、offset和长度即可读取。客户端保存本地.part、远程size/mtime和offset；恢复时取JSON记录与.part实际大小的较小值，并要求服务端确认远程size/mtime未变。当前方案核心流程完整，但没有强哈希，下载过程中也没有持续绑定文件版本；生产级应增加版本ID、分块/整文件SHA-256、窗口化传输、后台文件I/O和更细粒度并发控制。

### 10. 五个常见追问及参考答案

1. **问：为什么上传需要服务端状态，而下载可以无会话？**  
   **答：**上传半成品位于服务端，服务端必须记录.part路径、已确认大小、总大小、凭证和连接归属；下载半成品位于客户端，服务端读取块所需的文件名、offset和长度已经包含在请求中，可以直接读取正式媒体文件。

2. **问：上传恢复时为什么不能相信客户端记录的offset？**  
   **答：**客户端记录可能落后、提前或损坏，send成功也不代表服务端落盘。服务端把声明总大小、任务记录receivedSize和.part实际大小取最小值，修正文件和元数据后返回最终resumeOffset，客户端必须以该值覆盖本地记录。

3. **问：客户端或服务端重启后还能续传吗？**  
   **答：**上传双方都持久化状态：客户端保留源文件身份、服务器、任务编号和token，服务端保留.task与.part；只要源文件未变、任务合法未过期即可恢复。下载状态只在客户端，服务端重启后只要正式媒体文件size/mtime未变，仍可按offset读取。

4. **问：怎样避免下载恢复后拼接到另一个版本的远程文件？**  
   **答：**当前恢复初始化比较原size和mtime，不一致就拒绝。但同大小、同mtime或活跃下载期间替换仍可能漏检。生产级应由服务端返回稳定fileVersion和期望SHA-256，每块请求携带version，客户端下载完成后计算本地哈希比较。

5. **问：当前分片传输的主要性能瓶颈怎样优化？**  
   **答：**每64KiB等待一次RTT、上传每块fsync和全局锁、客户端GUI文件I/O都会限制吞吐。可使用有限滑动窗口、批量持久化或可配置耐久等级、每任务/分段锁、后台文件线程，并配合队列上限和速率控制。
